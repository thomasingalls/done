# Phase 542 — reduction writes a baseline past the released 4 MiB ceiling

Reduction ends by writing a local baseline that replaces the reduced history. Its record is JSON with every byte field in hex and was capped at 4 MiB (`LOCAL_BASELINE_LIMIT`); the encrypted carrier holds it in at most 17 chunks of 256 KiB. A candidate over the cap became `skipped: capacity`, the device showed the size-limit message and never reduced. Phase 541 removed the refusal before it in the same pass; this one is next, at "Building a smaller history snapshot…".

**Where the bound applies (read in code).** Encoding refuses on the raw snapshot and on the encoded record; decoding bounds the frame before parsing and each hex field inside it; the authentication message has the same bound; the carrier pointer limits packed bytes to 4 MiB + 32 and chunks to 17, and the reader checks every chunk's ciphertext length before copying it. The storage layer adds no bound of its own: a stored record is checked only for a 12-byte nonce and at least 16 bytes of ciphertext. The 17-chunk figure is also read by the startup census, the warm audit and the content store's key reads, which each ask for at most 19 keys.

**What fills a baseline (measured on the member fixture).** The encoded record is about twice the sum of the snapshot, the installed service-history record, the stream and own receipts and any carried sources, plus about 1.4 KB: 11,041 bytes from a 182-byte snapshot, a 2,483-byte history record and 2,167 bytes of receipts. The history record itself holds the service checkpoint's ciphertext in hex, so each byte of an installed service snapshot costs about four bytes in every later local baseline, on top of the current document's two. Without a history record the cap binds near a 2 MiB snapshot. With one installed from a snapshot of similar size it binds near 0.65 MiB, about half of the roughly 1.3 MiB the installation itself admits, so an account can install a service snapshot that no device can then reduce past. This is arithmetic from the codecs, not a reading from the affected account.

**The change.** The operator approved both the new carrier and the ceiling on 2026-11-11. A journal-era record, the only kind reduction writes, may now be read up to 32 MiB, but this build writes one only up to 8 MiB (`LARGE_LOCAL_BASELINE_WRITE_LIMIT`). Reading to 32 MiB means a later raise of the write limit needs no further format change, and builds from this phase on still open the larger records. A record without an era keeps 4 MiB for both. A reduced baseline whose packed bytes fit the released carrier is still written in `done/local-baseline-carrier/draft-3`, byte for byte as before. Only one that does not fit uses `done/local-baseline-carrier/draft-4`: counter v5, reduced history, 2 MiB chunks and still at most 17 of them; its parser refuses a pointer that would have fitted draft-3. The record tag, the authentication domains and the counter MAC tag are unchanged; the carrier name is inside the MAC'd counter tuple and every chunk's encrypted prefix. The complete-history writer refuses a candidate over 4 MiB as capacity before it reserves anything. A new carrier name is a construction change: the runtime census and construction registry record it under `account-local-baselines`, which stays open.

**Compatibility.** The operator accepted the consequence for older builds described below. Existing draft-2 and draft-3 records and draft-1 to draft-3 carriers read and authenticate unchanged. A reduced store and a no-era record written by the released code at `6a8de4bac`, before any source change, are kept as a vector; the new code opens them, reproduces their counter MAC payload, chunk prefix, authentication message and MAC, and replays the store to the same snapshot. On the released parsers, a draft-4 pointer throws "Unsupported local baseline carrier." (`app-update-required`), which startup shows as "This workspace needs a compatible app… Your saved data has been kept." Nothing is written, and the released census accepts the key count. So rolling back to an older build leaves a device that wrote a draft-4 baseline unopenable there until a newer build returns; a device that did not is unaffected. Two simpler shapes were observed to fail worse on the released code: 256 KiB chunks would need up to 129 keys, which its census stops as `repair-required` ("unknown-content-metadata") before it reads the carrier; a larger bound under the draft-3 name is refused as "Invalid baseline bound." (`repair-required`).

**Alternative not taken.** A binary record with raw bytes instead of hex, kept inside the released 4 MiB carrier, would roughly halve every baseline. It needs a new record codec, tag and authentication domain with its own canonical parser, and still a new carrier name so older builds refuse it as incompatible rather than corrupt. It buys about twice the headroom, which an installed service snapshot's fourfold cost can use up; raising the bound on the same codec buys eight times as much with less construction surface.

**What ceiling remains.** A new candidate past 8 MiB encoded, a raw snapshot of about 4 MiB less the other fields, is still `LocalBaselineCapacityError`, then `skipped: capacity` and the same park and message. Persisted bytes past 32 MiB, or past 4 MiB for an earlier carrier or a record without an era, remain integrity refusals. The encoder has one production caller, `summarizeBaseline`. It always builds a new candidate, from full history or from a stored predecessor plus its suffix, and decoding never re-encodes. So a device can always read and replay a record up to 32 MiB. A record between 8 and 32 MiB, which only a later build could have written, opens, but the device parks as capacity when it next reduces, because the new candidate is past this build's write ceiling. Before the counter is authenticated, a pointer that claims draft-4 can make the reader copy up to 17 × 2 MiB of ciphertext, where the released bound was 4.25 MiB. Other limits bind before this one: a service snapshot past about 1.3 MiB cannot be installed, which is being handled separately.

**Hex fields on WebKit (added after review).** The coordinator measured, and this phase reproduced, that WebKit 26.5 reports no match for `/^(?:[0-9a-f]{2})+$/` on valid input longer than 2,785,276 characters. It accepts 2,785,276 and refuses 2,785,278, quietly and in constant time; Chromium 151 and Firefox 153 accept 64 MiB of characters. Every baseline hex field (snapshot, history record, receipts, carried sources) was checked with that pattern. So on Safari and every iOS browser, the released code already refuses any field over about 1.39 MB of bytes. `encodeLocalBaseline`'s self-decode then throws a plain `Error('Invalid inbound frame')`, not a capacity error, and automatic maintenance halts as an owner error ("stopped because a storage or verification check failed") instead of parking. Nothing is written first: planning is a dry run, and the storage job runner closes the session only for repair-required or generation-changed codes, so sync continues and every reopen halts again. In released code that applies to snapshots of about 1.39 MB to 2.0 MiB; larger ones parked because the 4 MiB length check comes first. Phase 542 as first written would have halted up to the 32 MiB ceiling. A real owner probed with the pattern emulated confirms it: `removeHistory` rejects at 1.6 MiB and at 2.25 MiB, and the counter stays v2 with no chunks written.

The same pattern sat in four more parsers: inbound and private-delivery transport, spool and delivery wires, and source capsules. All five now use one character-code check, `lowerHexBytes` in `account-protocol/recovery.ts`, appended after every registered site there. It accepts exactly what the pattern accepted, non-empty, even-length lowercase hex, and decodes in the same pass. It returns nothing and zero-fills on refusal, and each parser keeps its own bound and error message. Spool and delivery wires (2 MiB) and inbound pages and envelopes (4 MiB and more) could pass the WebKit threshold. Source capsules cannot, since their 2 MiB bound keeps the field under 2.1 million characters, but they are fixed too: they are on the baseline path, and the threshold is an engine limit measured on one build. Left as they are: the journal's base64 pattern (16 KiB entries, off this path) and the flat `/^[0-9a-f]+$/` checks, which have no group and are correct at 64 MiB in all three engines. The engine probe and its output are kept with this record. It also found that spreading 200,000 arguments throws in Chromium; `contentStore.ts:412` and `inboundLedger.ts:596` spread one argument per stored row and are not changed here.

**Size and memory (Node, this Mac).** Codec alone, on a synthetic record: encoding with its self-decode takes 92, 180, 372 and 760 ms at about 4, 8, 16 and 32 MiB encoded. Peak RSS is 304, 482, 745 and 1,067 MiB, including about 72 MiB of harness. A whole reduction by a real owner (verify, build, encode, seal, write, readback, reload replay), two runs per size: 1.0–1.1, 2.2–2.4, 4.3–4.4 and 8.1–8.8 s, with cold reopen in 0.26, 0.52, 1.1–1.2 and 2.1–2.3 s. Peak RSS is 511–521, 637–653, 1,034–1,101 and 1,651–1,764 MiB, including about 135 MiB of harness and the in-memory fake IndexedDB. `hex()` builds one array slot per byte before joining, so a 16 MiB snapshot means 16.7 million slots, built twice per encode and once per decode. On these numbers 32 MiB is not a ceiling to build at on a phone; 8 MiB is, and these measurements are the basis for the operator's 8 MiB write ceiling. With an installed service snapshot at the install limit, an 8 MiB ceiling still carries a document of about 1.33 MiB.

**Tests and runs.** Fifteen cases in two new files. `test/localBaselineLargeCarrier.test.ts` has ten:
- a real Account owner saves 2.25 MiB of text, reduces into draft-4, reopens cold, reads the text back and reduces again;
- a small history still writes draft-3;
- the released vector opens and authenticates byte for byte;
- bound and carrier refusals keep their kind, including persisted bytes past 32 MiB as integrity;
- a short draft-4 chunk refuses before it is opened;
- the 8 MiB write ceiling and the no-era ceiling are capacity for a new candidate;
- a reduction just over 8 MiB parks and writes nothing;
- one just under completes in draft-4 and reads back;
- a draft-4 record of about 9.5 MiB, stored as a later build would store it, reads, authenticates, replays and opens cold, and its next reduction parks;
- the complete-history writer refuses before reserving.

Five of the first seven failed on the released code, and two are guards that pass on both. `test/hexFieldValidation.test.ts` has five. They emulate the measured WebKit result in Node and pin the accept and reject set through every changed parser: empty, odd length, uppercase, non-hex at start, middle and end, exactly at the bound and one byte past it. Four failed before the repair and one is a guard. One existing case in `test/localBaseline.test.ts` that pinned the 4 MiB refusal is restated at the 8 MiB write ceiling. Typecheck passes, and format and lint pass on the changed files. On the finished tree the full unit suite passes with the CI command, `pnpm test --maxWorkers=1`: 340 files, 3,302 cases, one existing skip, 331.02 s, with the host load average near 8 and an unrelated Lean build from another worktree running alongside. `pnpm build` passes at 308.5 of 350 kB, and `pnpm trace:check` passes once the contract checks are rerun on the finished tree.

Bookkeeping follows [development.md](../../../development.md#release-bookkeeping). The ten CI contract checks pass. Both new files are reviewed Vitest selections: the case denominator moves from 2,661 to 2,676 and the planning inventory to 1,110 obligations with 552 unresolved; the nine adapter files pass 178 cases. The runtime census gains the draft-4 label and records 30 registered site moves: ten in `localBaselineRecord.ts` and `localBaselineAnchor.ts`, and twenty in the files of the five hex parsers. The construction registry follows them. `pnpm account:crypto-prep` passes; `pnpm account:crypto-audit` passes its registry step and stops at 16 open constructions, as on `main`. No file under `vite/` anchors a changed source. Twenty-four node test files that import the changed protocol and storage modules, plus five parser-conformance files, pass 30 of 31. The failure is `account-parser-conformance/baseline.test.mjs`, which swaps in a frozen `spoolRecord.ts` from `f0b6acd2` that lacks exports current modules import. It fails independently of this change and is not in CI.

Limits. This seat ran no browser suite, native suite or device. The coordinating session ran two browser suites. `pnpm storage:compatibility` passed 17 of 17 on the tree before the hex repair; a rerun on the final tree is pending. `pnpm test:local-baseline` fails 5 of 5 because the page-side `__baselineOwner` hook is undefined. Four of the five fail the same way on clean copies of main `e9ec1e697` and of the branch tip `6a8de4bac` without this phase; the fifth needs git history and could not be compared in a copy. That failure predates this phase, but it leaves the draft-4 path without real-browser coverage: its storage behaviour is verified only against the unit suite's simulated IndexedDB. The engine probe covers the hex checks only; time and memory for a whole reduction are measured in Node, where fake IndexedDB holds the store in memory. Every size figure for the affected account is inferred, and none of the earlier measurements is from its devices, so whether the old ceiling would have bound on that desktop is unknown. The operator's 2026-11-05 note that a different ceiling or encoding needs an explicit format and limit decision is met by the two approvals of 2026-11-11. No commit or deployment.
