# Phase 544 — no device publishes a history snapshot that devices cannot install

A device can publish a history snapshot to the service ("History maintenance", then "Create history snapshot"), another approved device verifies it, every device installs the latest one, and "Prune covered history" then removes the service's older records. Creation allowed 16 MiB of document state. Installation allowed about 1.33 MiB. Nothing checked the difference.

**Every bound, read in code.**

- Creating, on the device. `createHistoryCheckpoint` refuses a plaintext update over `GENESIS_LIMIT` (16 MiB), and `openHistoryCheckpoint` refuses the same on reopening. `parseHistoryCheckpoint`, used everywhere a checkpoint is read, bounds its JSON at `HISTORY_CHECKPOINT_LIMIT` (72 MiB) and its ciphertext at 16 MiB plus the 16-byte tag (twice that in hex characters). It also bounds publishers at 192, sources at 129, and coverage vectors at 16 MiB together. A saved attempt is bounded at `HISTORY_PROGRESS_LIMIT` (about 72 MiB), and the custody record that holds it at `HISTORY_PAGE_LIMIT` plus 16.
- Publishing. A request is bounded at `HISTORY_EXCHANGE_LIMIT` (72 MiB plus 8 KiB) by the client parser and by the service's HTTP route. The client transport and the service's request timer each stop a request at 10 seconds; that limits time, not size. The service checked a proposal's signature, ancestry, cuts and sources, but not its size beyond the parser's.
- Admitting. `admitHistoryCheckpoint` opens the snapshot under the 16 MiB bound only. The service admitted it under the same checks as publishing. A stored row is read back only if it is under 72 MiB plus the admission limit.
- Installing. The receive path reads the latest admitted snapshot and builds an install event (`encodeHistoryInstall`): the reader fields, the whole checkpoint with its ciphertext in hex, and the admission. The event alone over `MAX_BATCH_BYTES` (4 MiB) raises `HistoryInstallSizeError` before verification. `verifyHistoryInstall` then authenticates the admission, decrypts, checks coverage and ancestry, re-derives the update, and raises the same error if the update plus the event exceeds 4 MiB. The commit (`appendInbound`) stores exactly those two records, and `copyBatch` refuses a batch over the same 4 MiB, so the install check is the storage batch bound. Cold replay of the ledger and of a local baseline re-run `verifyHistoryInstall` under the same bound.
- Later. Every local baseline the device writes carries the install event in hex, about four bytes per snapshot byte, under the 8 MiB write ceiling of phase 542. Enrolling or recovering a new device is separately bounded at 4 MiB of merged document state.

**The largest installable snapshot (measured).** The update a device re-derives equals the sealed plaintext, byte for byte, in every case measured: a single text, a document with 2,000 edits and deletions from two writers, and the boundary sizes. The install event is twice the plaintext plus 32 hex characters for the tag, plus a remainder of about 2,000 bytes: the reader fields, manifest, signatures and admission, with the coverage vectors counted four times (in hex, in the manifest and again in the admission), about 140 bytes per further publisher and about 180 per source reference. So a device can install a plaintext of at most (4,194,304 − 32 − remainder) / 3 bytes. On the single-writer fixture that is 1,397,416 bytes, 1.33 MiB; a reader with a one-digit epoch can take five more characters. Each byte of the delete set costs four thirds of a byte of snapshot, so a heavily edited document reaches the bound sooner. "Document state" here is the encoded Yjs update, deleted content included, not the visible text.

**What happened to a larger snapshot before this phase.** Verified by tests run against the base tree, with only the new measuring function added: the producer saved and published it, a device verified it, the service admitted it, and the service pruned past it. The base client created and admitted one 2 bytes over, resumed and published a saved one, and pruned over one; the base service accepted the publication, the admission and the prune ([base-tree runs](./base-tree-runs.txt)). The installer refuses it, also verified by test. The rest is read in code and not run end to end:

- The producer showed "Snapshot saved. Verify it from another approved device." The verifying device then showed "Verified snapshot N is saved."
- From then on, each device whose receive path fetches history tries to install the latest snapshot at the start of every receive pass, at most every five seconds. A device fetches history once its membership epoch is past 3 or its generation past 1, or once it has installed or inherited history or continues a membership. The pass ends as `blocked: inbound-size` before any stream is read, so receive halts. That includes the producer and the verifier. After 30 seconds the device shows "Changes from your other devices are not arriving here.", "Reason: receive:inbound-size" and "Retry receiving". Retrying or reopening repeats it. Sending is unaffected.
- A device that has never fetched history (for example both devices of a two-device account at epoch 3 with no membership change) is not affected by the snapshot itself.
- After a prune, the service has replaced accepted decisions at or below the previous snapshot's cuts with ciphertext-free receipts, and reads there return `unavailable`. A device behind that point can continue only by installing the latest snapshot. If it fetches history it stays halted as above. If it does not, its receive retries as `network-unavailable` indefinitely; this second case is inferred.
- No recovery inside the account. A later snapshot covers the earlier one and cannot be smaller. Discarding applies only to an unadmitted proposal, and an admitted latest snapshot cannot be withdrawn. A removed and re-enrolled device starts from a handoff bounded at 4 MiB of merged state, which might work for a document between 1.33 and 4 MiB; that is untested.

**The guard (client).** `historyInstallBytes` (in `account-protocol/historyCheckpoint.ts`, shared with the service) computes what a device's installation needs from the checkpoint alone. It counts the plaintext length from the ciphertext, plus the exact install event that `encodeHistoryInstall` would build for the widest reader: the admission's fields are fixed by the checkpoint, and the reader's epoch is taken at 16 digits. A test pins the figure byte for byte to the encoder for both install versions, pins `HISTORY_INSTALL_LIMIT` to `MAX_BATCH_BYTES`, builds the largest snapshot the guard accepts, installs it and stores it as one storage batch, and shows the installer refusing a snapshot six characters larger. `createHistoryCheckpoint` now also refuses if the re-derived update is longer than the plaintext, which is what lets the ciphertext length stand for it; that has not happened in any measurement. The one place that decides is `runHistoryMaintenance`, the interface the History maintenance menu already uses:

- `create` prepares the snapshot as before, then refuses before saving progress or sending anything;
- `resume` refuses to publish a saved proposal of its own that is too large;
- verifying refuses to admit a pending snapshot that is too large;
- `prune` refuses while the latest snapshot is too large;
- `inspect` reports an oversized pending or latest snapshot.

Each returns a status with `tooLarge: { snapshot, needed, allowed }` instead of throwing, because Worker errors reach the page only as codes. The session bridge accepts the field under a closed check. The view shows one sentence per case, in MiB to one decimal, "just over" when the two round alike, and hides the action the snapshot would refuse:

- "This workspace is too large for a history snapshot. Installing one on your other devices would take 4.6 MiB, and this version installs snapshots of up to 4.0 MiB. Nothing was saved or sent. Your writing is unchanged."
- "The saved snapshot is too large for your other devices to install (4.6 MiB; this version installs snapshots of up to 4.0 MiB), so it was not sent. Discard it. Your writing is unchanged."
- "The snapshot waiting for verification is too large for devices to install (4.6 MiB; this version installs snapshots of up to 4.0 MiB), so it was not verified." It then says "Discard it." to the device that made it and "It can be discarded from the device that made it." to others, followed by "Your writing is unchanged."
- "The latest verified snapshot is too large for devices to install (4.6 MiB; this version installs snapshots of up to 4.0 MiB). Covered service history cannot be removed while it is the latest snapshot. Your writing is unchanged."

**The service.** It cannot open a snapshot, but `historyInstallBytes` needs only the checkpoint. It now refuses with `checkpoint-too-large` to keep a new proposal, to admit a pending one, and to prune while the latest is too large. It still serves an existing oversized snapshot to readers, so a device can say why it cannot install it, and still lets its producer discard it. All three refusals sit before any write. Rollout:

- Service first: an older client that creates an oversized snapshot has its publication refused and keeps a saved attempt. Its view offers only "Resume", which fails with the general "could not finish" message, so it cannot make another snapshot until it updates. The account is unaffected. An older client's verification of, or prune over, an oversized snapshot left from before the update fails the same way. That is the intent: no device is stranded.
- Client first: updated devices never publish, admit or prune past an oversized snapshot, and name existing ones, but a not-yet-updated device can still do all three through the old service.
- Both: no new oversized snapshot can become pending, admitted or latest. An oversized latest snapshot admitted before the update still halts receive on devices that fetch history, and pruning stays refused while it is latest, which is permanent because no later snapshot can be smaller.

**Already-blocked devices and reduction.** `HistoryInstallSizeError` now carries its sizes. A receive halt from it keeps the reason `inbound-size`, so halting and retry are unchanged. It carries a presentation detail `{ cause: 'history-snapshot', needed, allowed }`, kept beside the halt by the scheduler and cleared with it. The bridge drops a malformed or misplaced detail. The sync notice says: "Changes from your other devices are not arriving here, because a history snapshot saved on the service needs 4.2 MiB to install and this version installs snapshots of up to 4.0 MiB. Your writing on this device is kept." On reduction, `planLocalRetention` maps the error to a `capacity` park with a new phase 543 cause, `installed-snapshot`, and its sizes: "A service history snapshot installed on this device needs 4.1 MiB to check, and this version checks snapshots of up to 4.0 MiB." Integrity handling is unchanged. The size error is raised on replay only after the record has authenticated, and any other failure of the same check still rejects; a test asserts both. That park is not reachable with this build, as phase 543 found.

**Not done: skipping.** Naming the halt does not end it. A device could skip a snapshot it cannot install and keep reading streams, as it already does when installing one needs retired history (`RetiredHistoryRequired`). That would restore receive on an account holding an oversized latest snapshot, unless the service had pruned positions the device still needs; such a device would then retry as `network-unavailable` with no named cause. The halt has been a deliberate choice since 2026-10-09, so changing it is left to the operator.

**The limit that remains.** A workspace whose snapshot would need more than 4 MiB to install, a document state of about 1.33 MiB less four thirds of its coverage vectors, can never have a service snapshot. Its service history therefore can never be pruned, and the guard now says so instead of stranding devices. The 8 MiB baseline ceiling from phase 542 binds at almost the same place on a device that has installed a snapshot near the bound. Its baselines carry about 4P for the history record plus 2D for the document. At P = 1.33 MiB that leaves D of about 1.33 MiB, so its reduction parks as `snapshot-size` once the document grows past the snapshot. Without an installed snapshot, reduction binds near a 4 MiB document. Raising the install bound means changing what is installed, not one number:

- A larger batch only for installation keeps the atomic commit and the event shape. But the baseline carries 4P, so the 8 MiB write ceiling then parks reduction straight after any such install.
- An install event without the ciphertext (a new event version): keep the exact decrypted plaintext as the content record, and on replay re-seal it with the generation key, the checkpoint's nonce and its associated data. That rebuilds the exact ciphertext, so the producer's signature and the admission still verify. It removes the 2P of hex from both the event and every later baseline, bringing the install bound near 4 MiB of plaintext and the baseline cost to about 2P. It changes a stored format and the replay proof.
- A chunked install across several storage transactions: needs a resumable install journal with begin and commit markers that cold replay understands, because the atomic witness transition is lost.

Each also meets memory on phones (phase 542 measured an 8 MiB baseline reduction at 1.6 to 1.7 GiB peak in Node) and the 10-second request timers on both ends for the upload and download.
