# Phase 545 — a baseline replay builds its coverage view once; a return to the app stays due until a full read completes

Both parts were agreed by the operator on 2026-11-11 after the read-only foreground investigation and its Node probe. Options E (physical-only resume) and F (invalidate only after real suspension) were not approved and are not here.

## Part 1: one coverage view per replay

**What was wrong (measured).** Every forced read and every cold open of a reduced device replays the local baseline (`replayLocalBaseline`). Each coverage check in that replay called `verifyInboundCoverage(records, updates)`, which builds a new Yjs document from the whole snapshot plus every saved update, then throws it away. A replay made one such call per source capsule in the census (line 840 before this phase), one per capsule carried in the baseline (724), one for an installed history (748), one per stream and own receipt (662 via `verifyReceipt`) and one for the self-receive advance (834). With N capsules saved since the last reduction and no carried sources, a replay built the document 7 + N times (6 at N = 0); each build hashes, decodes and applies the snapshot and every suffix update. The investigation's probe measured exactly that count at N = 0, 1, 2, 5, 10, 20, 50, 100 and 200 on `9882e30cd`, identical for a forced read and a cold open; the before run below repeats it at 0, 50 and 200.

**The change.** `createPassCoverage(records)` in `src/crdt/inboundLedger.ts` gives a replay one view over its captured rows. It binds `createInboundCoverage()` (no incremental append, no direct shortcut, no prepared baseline: the same `contentCoverage` flags `verifyInboundCoverage` uses) at the first check, and every later check in the pass goes to the same view. `replayLocalBaseline` creates it once after assembling `records`, passes its `check` to all five call sites (`verifyReceipt` now takes that function instead of the rows) and clears it in its `finally`. `full()`, the complete-history replay, already does the same ("Rebuild once", `localBaselineReplay.ts` around 274). `verifyInboundCoverage` is unchanged and stays exported as the per-call reference.

The continuation cache needs no change: `createBaselineReuse` builds no document when it is created, and `advance` already binds one incremental view (`coverage.bind(candidate)`, `src/crdt/localBaselineReuse.ts` around 216 to 258) and checks every newly indexed capsule against it. Its single build per full read does not grow with capsules. `verifyInboundLedger`'s own view (one per call, with the direct-proof shortcut on) is a different proof mode and is also one per replay; it is unchanged.

### Equivalence argument

**What one `verifyInboundCoverage(records, updates)` call guarantees.** It builds a fresh document (garbage collection off) by decoding and applying every `update` and `state` row of `records` in sequence order; a malformed row throws there. It indexes those rows' exact bytes as originals. Then, for each update in order, it accepts the update if its bytes equal a row's or an update already proven in this call; otherwise it forks the document (encode and decode, with pending structs and pending deletes copied), applies the update to the fork and accepts only if the fork's state equals the document's, pending state included. Anything else throws `ContentError('repair-required', 'Inbound content coverage is missing')`, and a malformed update throws from Yjs. Each verdict depends only on the bytes of the content rows and of the update.

**What the shared view keeps between calls, and why no verdict changes.**

1. *The document.* Built from a private copy of the same content rows, sorted the same way, with the same flags. A check never mutates it: `forkDoc` encodes a shallow copy of the document with its pending fields set to null and decodes into a new document, and `sameDocState` reads snapshots. So it is the document the per-call path would build from the same rows.
2. *Originals.* Fixed at the build.
3. *Proven positives.* A bounded index of byte copies of updates already proven covered against this document. Coverage is a function of (document, update bytes), so skipping the re-proof of identical bytes gives the per-call verdict. They are copies, so a caller erasing its buffer after a check (`verifyReceipt` fills the decrypted updates, `eraseCapsule` fills decoded sources, the self-receive generator erases its capsules) cannot affect them. The index may clear itself at 4 MiB or 4,096 entries, which only drops the memo.
4. *The rows.* The view holds a copy; the per-call path reads the caller's rows at each call. They could differ only if a content row changed between checks. In `replayLocalBaseline`, `records` is one const array: the authenticated snapshot (owned by the decoded baseline and erased only after the replay returns), the carried capsule records (`outbound`, not content) and `captureInput` copies of the suffix. Between the first and last check the pass runs `decodeSourceCapsule`/`eraseCapsule` (fresh buffers from `lowerHexBytes`), `inspectInbound`, `verifyBaselineAuthority`, `verifyHistoryInstall` (fills only its derived update), `verifyReceipt` (fills only decrypted updates), `verifySpool` and `verifyDelivery` (fill only their decoded originals and bodies), `verifyInboundLedger` (builds its own view from references and clears it without filling unbounded originals; fills only decrypted updates and its captured receipt copies) and `advanceSelfReceive` (erases its own decoded capsules). None writes an `update` or `state` row of `records`, and none reorders or replaces the array. A record set that differs between calls therefore cannot occur in a replay, and the bound view refuses any other array (`Coverage view was invalidated`).
5. *Order.* Each verdict is a pure function of its inputs and the memo only skips identical bytes, so any order of checks gives the per-call result.
6. *Refusals.* The first refusal throws the same error type and message. The replay has no catch that continues after a coverage error: its only catch maps `RetiredHistoryRequired`, which coverage never throws, and `advanceSelfReceive` has none. So no check follows a refusal, and the pass also refuses any later check by construction.
7. *When the document is built.* At the first check, where the per-call path first builds, so a damaged content row refuses at the same point with the same error. `documentState(records.slice(0, 1), true)` still runs before any build and refuses `ineligible` first, as before.

**Tests of the argument.** `test/baselineReplayCoverage.test.ts` keeps the per-call path as the reference: a mock of `createPassCoverage` that, when switched on, sends every check to `verifyInboundCoverage` over the same rows. The replay is imported before `inboundLedger` because the two form an import cycle (`inboundLedger` reaches `localBaselineReplay` through `historyInstall`, `custody` and `contentStore`); a replay first loaded inside the mock factory would bind the unmocked module, and an early version of this test passed vacuously for that reason. The replay tests now assert that the reference really ran its checks; the primitive test calls both paths directly.

- *Primitive, 150 generated runs.* Two writers, mixed text, map and merge edits; captured rows are a delivered subset, sometimes with a damaged row; each call gets fresh buffers, sometimes altered, malformed (`[255]`) or a merged update, and the caller erases them after the call. Per call, the pass and `verifyInboundCoverage` give the same verdict or the same error, through the first refusal, after which the pass refuses. Neither path changes the caller's rows.
- *Replays, 60 generated runs.* `memberFixture` histories with own positions, unallocated capsules (carried in the baseline), peer receipts and installed histories before the cut, and own, unallocated and peer rows after it. Each run applies one of: no tamper, a dropped suffix content row, an altered update row, a duplicated capsule, a reordered capsule, a re-signed baseline whose snapshot lacks one independent original, or a duplicated update row. Results (canonicalized, including census, delivery, inbound state and snapshot) or refusals must be identical. With seed 545012: 39 identical results, 17 identical coverage refusals and 4 other identical refusals; 21 runs carried sources, 26 had an installed history, 41 had suffix capsules; the reference made 296 checks.
- *Each site.* Re-signed snapshots missing a carried source's original, an installed history's state or the latest own update refuse identically with the coverage error, at the first, first and second check (history after a carried source), and at a receipt check respectively; the intact baselines replay identically.
- *Mutation control.* A shared view that checked only its first call failed all three tests.

The record-set case asked for cannot be generated, for the reason in item 4.

## Part 2: a return to the app stays due until a full read completes

**The gap.** `load()` cleared `forceFullRead` before its physical read. A read interrupted by `MaintenanceInterrupted` keeps the previous view on purpose, so the flag was gone and the view was still there. On a return to the app, the overdue background audit (`auditWarm`) could take the pending full read first, be interrupted by the receive pass's queued job, and leave the receive pass, and every load after it, on the warm path, with no full read before reuse. The 2026-10-12 decision requires one. On the base source, the new tests show the next foreground load reading nothing, and on an unreduced owner a load after an interrupted resume read returning rows that a damaged interior row should have refused.

**The change.** `contentStore.ts` keeps a separate `resumeFullRead` flag. `invalidateWarm()` (called by `accountCapture.ts` on visibility return, `resume` and `pageshow`) sets it with `forceFullRead`. Any load that ends without completing re-arms `forceFullRead` while it is set, including an interrupted maintenance read. A full read that completes clears it, unless another invalidation arrived during that read, in which case the existing recursive re-read runs and the flag stays until that read completes.

**The semantic-audit test is kept, and the two requirements do not conflict.** `test/localBaselineWarm.test.ts` (around 193 to 214) pins that an interrupted *reference* (oracle) full read does not move onto the next foreground load, and the ledger's comment says the same ("A cancelled audit stays due, but must not migrate onto the next foreground edit"). That read checks the incremental verifier's own correctness and stays due on its own schedule. A return to the app is a different request: the decision requires a complete read before warm reuse. The two used one flag. Now `auditWarm`'s internal oracle requests still set only `forceFullRead`, and the ledger's semantic audit (`accountReceive.ts` audit `run`) calls the new `requestReferenceRead()` instead of `invalidateWarm()`, so both keep their previous behaviour exactly. That test passes unchanged. A new case pins the same for `requestReferenceRead()`.

**The second full read.** Not avoided. The recursion re-reads only when an invalidation arrives after the current full read has begun, that is, after the load took the flag and just before its read transaction. Skipping it would need proof that the hidden period behind the later event ended before that transaction began, and the forwarded events carry no time. It is rare and stays as it was.
