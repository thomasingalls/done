# Phase 541 — reduction continues past the resumable cache instead of refusing

A device whose saved history was larger than the resumable preparation cache could never reduce. On 2026-11-11 the operator's production desktop, which had never reduced, stopped at "Reading saved history…" and showed the size-limit message. During that stage every saved record is decrypted through the cache, which refused at 32 MiB or 131,072 entries; the scheduler mapped the refusal to `capacity` and parked. The ledger's fast verification path also stops at 32 MiB of raw record bytes, so both ways out closed at about the same size. The document itself exports to about 142 KB.

Mapping these refusals to a park was item 1 of the release-hardening plan, and "retention parking at capacity" was carried as open debt (phase 442). The cache exists so an interrupted reduction can resume. Without it there is no budget, only the need to finish in one pass, and phases 539 and 540 now give an attempt an uninterrupted window it did not have when the park was designed.

When the cache cannot take a result it now returns that result uncached, marks itself full, keeps nothing more and stops pausing to save slices for the rest of the pass. A saved slice that does not fit on import is left out whole. Each journal is told how much its saved checkpoint can still take, so it never keeps a slice the checkpoint would refuse; the storage guards remain as defensive refusals. A history too large to bind any saved journal runs the pass with no journal at all. No limit value, stored format or wire format changes.

Later stages do not depend on the cache. Each cached result is bound to its exact input bytes, slot, context and verifier identity, and a miss runs the same verifier as the path with no journal. Row placement, the counter check, candidate building and comparison, plan coverage, inventory equality at commit, readback and the reload replay never consult it. This is from reading the code.

Two owner-halt hazards were found on the way and repaired. Saving a slice could halt the owner when it held more values than one encoded value allows or passed 32 MiB with its frame; a slice now pauses at 32,767 rows and accounts for its framing. The coverage basis encoded every content row into one value and threw on large content; it now falls back to uncached coverage checks. Neither was observed on a device.

An uncached pass leaves nothing to resume. If routine queued storage work cuts one short it now returns `capacity` and parks through the existing path, so the same history is not retried in a loop; a changed history, "Check again" or reopening tries again, and local writing still yields and retries as before. Review here added one repair to the reduction owner: a capacity refusal that arrives after the five-minute hold has lapsed now still spends the hold, where before each changed hint could engage another.

Two cases that pinned the refusal are restated and ten are added across five existing test files; no new test file, no deadline changed. The reviewer's rerun of nine affected files passes 106 cases, and the typecheck and the five account-sync source-anchor controls pass. The ten CI contract checks pass, and on the finished tree the full unit suite passes with the CI command, `pnpm test --maxWorkers=1`: 338 files, 3,287 cases, one existing skip, 272.44 s. The case denominator moves from 2,660 to 2,661 with the planning inventory unchanged at 1,108 obligations and 552 unresolved. The runtime census is refreshed after review: no changed line contains a domain label or cryptographic call, and three registered sites in `localRetentionPlan.ts` move one line with the construction registry following them.

Limits. No browser, native or device run and no timing. Whether the desktop's pass fits the five-minute hold is an inference from phase 495 (2,155 positions, 14,466 rows, 93.9 s over 11 slices on a lab Mac). The cache fills with decrypted rows first, the cheapest work to redo, so an interrupted pass restarts almost from scratch; caching verification results first would make resuming useful and is not done here. The 4 MiB encoded-baseline guard is unchanged and may be the next limit this device meets, at "Building a smaller history snapshot…", with the same message. Peak memory for a completing pass is higher than for one that refused early. No deployment.
