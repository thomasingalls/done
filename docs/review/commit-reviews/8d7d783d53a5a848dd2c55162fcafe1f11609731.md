## Change seen while moving backward

The parent loses the recovery-code selection, generator, vectors, and progress closure. This commit fixes the storage
half of row 14 at 25 Crockford Base32 symbols (125 generated bits), rejects password stretching, specifies the sealed
`R_priv` envelope and confirmation/normalization rules, and sketches the network-facing replacement step-up for 3b.

## Original-contract trace

It answers the entropy/KDF portion of `OC-034` and `OC-076`: every account has a saved and re-entered high-entropy
code sealing the recovery private key, with optional independent PRF wraps. It supports `OC-039`/`OC-082` by making
encoding, normalization, rejection, keypair, seal, and tamper behavior executable.

## Construction and state-machine effect

Generation draws 25 independent bytes and maps each with `byte & 31`, yielding a uniform alphabet symbol per byte.
Display is five groups of five; normalization removes separators/case and maps `O→0`, `I/L→1`, while rejecting
wrong length or non-alphabet input. HKDF-SHA-256 over the full 25-character code and fresh salt derives the AES-GCM
seal for the 32-byte X25519 scalar; principal/version are bound through AAD. Account setup must re-enter the code.
Replacement requires content access plus an account-credential challenge, but that network half is explicitly draft.

## Assumptions and guarantee boundaries

- The no-stretch conclusion is conditional on a generated, full 125-bit code that is never chosen, extended, or
  truncated by a person. Any relaxation reopens the KDF decision.
- The service can hold the sealed recovery envelope but not test candidates cheaply enough to matter at 125 bits.
- One fresh salt produces a fresh derived key per seal; AES-GCM nonce safety is argued through one message per key.
- Confirmation is a durability boundary: setup does not succeed until normalized re-entry matches.
- The replacement challenge is network-facing review-3b work, not evidence needed to select storage entropy.

## Evidence and oracle independence

The generator enumerates all 256 byte values to prove eight preimages per Base32 symbol, cross-checks normalization and
rejection cases, derives the RFC 7748 public key from the published scalar, round-trips two principal-bound seals, and
executes tamper negatives. The exact archived check passes. Its primitive keypair oracle comes from an external RFC,
while its composition producer/checker still share code. The worked replacement challenge at this SHA has no
independent service state or replay negative.

## Consequences and residual failures

The selection removes an unnecessary password-hardening dependency and its bundle/latency variability without
reducing an already impractical offline search. It also makes transcription acceptance precise. At this SHA the
phrase “single-use service challenge” is not true by construction: the challenge is a pure function of principal and
new public key, so an assertion can be replayed until separate service state rejects it. Because that half is marked
draft/3b and is later corrected before protocol selection, no pinned-tip finding survives.

## Falsification attempt and counterevidence

I recomputed the entropy mapping: masking a uniform byte gives each of 32 symbols exactly eight preimages, hence 125
bits across 25 independent draws. At `10^12` guesses/second, exhaustive search remains about `1.35×10^18` years.
I tested whether permissive Crockford normalization reduces generated entropy; it expands accepted spellings of the
same 125-bit value but not the candidate set. The real counterexample was replay: identical operation inputs produce
an identical “single-use” challenge. Later `ff0b48f` explicitly recognizes and repairs that defect.
