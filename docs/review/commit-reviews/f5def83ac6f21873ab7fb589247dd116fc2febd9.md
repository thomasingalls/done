## Change seen while moving backward

The parent loses the device-lock selection, generator, vectors, and progress closure. Row 13 returns to an open
choice over factor derivation, enrollment migration, and copy. This commit chooses a generated-code root, an optional
PRF convenience seal, an atomic custody migration, and forward key rotation.

## Original-contract trace

It answers `OC-026` and `OC-075`: the optional local factor replaces promptless custody without becoming account or
recovery proof, and loss can destroy the last Local copy only after explicit disclosure. It also protects `OC-023`
and `OC-029` by retaining ciphertext-only persistence and rotating away from a pre-enrollment profile copy.

## Construction and state-machine effect

Every enrollment generates a 25-symbol/125-bit code. HKDF-SHA-256 derives a code seal key; WebAuthn PRF, where
available, supplies a separately domain-separated additional seal of the same random `L_lock`. Enrollment stages
new factor seals and generation envelopes while `L_local` remains usable, then one IndexedDB transaction swaps staged
envelopes, deletes `L_local`, and sets custody `locked`. A separate ordinary content-key rotation clears persistent
`rotation_owed`; history stays under retained old generations because a pre-enrollment copy already has it.

## Assumptions and guarantee boundaries

- Generated full-entropy codes, never user-chosen or truncated, make offline stretching unnecessary.
- The PRF is additive convenience, so platform absence does not weaken the mandatory code tier; however, the browser
  support floor is asserted rather than documented.
- IndexedDB can atomically update custody/envelopes/delete `L_local` in one transaction.
- Before Stage 4 rotation is unilateral. After other devices exist, immediate local invocation of ordinary rotation
  is explicitly uncertain and represented by `rotation_owed` plus conditional copy.
- Same-origin hostile code remains outside the factor's protection; the guarantee is file-level custody.

## Evidence and oracle independence

The generator verifies all eight role/slot PRF inputs differ, both code and PRF seal/open paths, failure of a wrong
factor, atomic-record shapes, custody tiers, and byte-for-byte reuse of row 3's envelope vector. The archived exact
generator reproduces cleanly. It cross-checks two separately introduced artifacts rather than inventing a new
envelope model, although producer and checker remain one JavaScript program and no browser persistence transaction is
executed here.

## Downstream propagation

`dbfd01f` folds row 13 into the PRD/TRD but drops the pending-rotation/copy contingency. Later protocol rotation
selections add service intent/outcome rather than disproving that soft joint. The pinned tip still carries the
original selection, generator, `rotation_owed` field, and unconditional normative copy side by side.

## Consequences and residual failures

The construction avoids the two catastrophic enrollment states: deleting the default opener before resealing, and
claiming protection while never rotating away from a copied `K_g`. Factor loss is intentionally a durability loss at
the last Local replica. Remaining risks are operational: PRF availability needs a support floor, and multi-device
enrollment needs an explicit completion boundary when rotation is owed.

## Falsification attempt and counterevidence

I tried the obvious alternatives: treating PRF as the sole factor makes portability/platform availability a security
branch; using a passphrase reintroduces unrateable offline guessing; deleting `L_local` first can brick the only copy;
resealing without rotation lets the old profile read future content; rekeying history cannot revoke a copy that
already holds it. The selected ordering survives those attacks. The one unresolved counterexample is loss of service
during post-enrollment rotation, which the record itself identifies and safely persists rather than hiding.

## Nuance preservation

The selection is unusually explicit about what it does not prove: file exposure only, PRF floor not verified,
forward-only protection, recovery cannot bypass the lock, and immediate rotation after Stage 4 is a soft joint. That
nuance is complete at this commit; the first divergence occurs in the following requirements fold.
