## Change seen while moving backward

Returning to `130757d` reopens row 12, restores an Argon2id-derived-verifier candidate, removes the discoverable

## Original-contract trace

The selection answers OC-074: an offline slot verifier with offline-guessing resistance that grants no network
authority. It preserves OC-016's account boundary, OC-018's sign-out-retains-slot behavior, OC-023's distinction
between a profile reader and same-origin execution, and OC-039/OC-079's browser-origin threat boundary.

## Construction and state-machine effect

Account creation requests a discoverable WebAuthn credential, preferring Ed25519 and accepting ES256. The service
signs a versioned binding over account, principal, RP ID, epoch, credential id, and SPKI public-key bytes. A closed
slot stores that binding; reopen first verifies the service signature, returned credential id, parsed client data,
RP-ID hash, UP/UV flags, and assertion signature over a nonce-bound slot challenge. Success opens already-local state
only. Network session/authentication remains a separate online ceremony, and optional device lock remains a second
gate after slot proof.

## Assumptions and guarantee boundaries

The private credential key remains in a user-verifying authenticator, the stored SPKI encoding identifies one of
two compiled-in algorithms, and the retained authorization lineage verifies the binding's epoch. A usable
authenticator is runtime-dependent; without one the product offers no password-shaped fallback. A stale binding may
reopen local bytes until the device observes revocation, and anyone executing the origin under default custody can
still use already-open key handles. The slot verifier is therefore shared-installation access control, not stronger
content custody or network authority.

## Evidence and oracle independence

The generator verifies Ed25519 and ES256 keypairs, both bound-key encodings, positive assertions, two documented
successful residuals, and 22 negatives including public-key substitution and challenge-field isolation. WebCrypto
is an independent primitive implementation but ceremony generation and verification share project code and no
browser authenticator participates. W3C §7.2 supports checks for type, challenge, origin, RP ID, UP/UV, and
signature, but also requires RP policy validation for `crossOrigin` and `topOrigin`; the project verifier parses
neither, while its positive client data always fixes `crossOrigin: false`.

## Downstream propagation

The construction reaches PRD §§6.1 and 6.7; TRD §§10.11, 11.1–11.2, 13.9–13.10, 15, and 16; the row-1 suite
through ES256; row-13's now-unused PRF role; generated vectors; decisions/progress; and later row 14's recovery
step-up, which reuses the same credential and ceremony.

## Consequences and residual failures

The absence of a stored secret removes an offline guessing oracle, while the service signature prevents a profile
editor from substituting an attacker-controlled public key. Offline use and sign-out semantics remain intact. A
device without an authenticator cannot create the account credential. The abstract verifier accepts valid assertions
from an unapproved cross-origin embedding context, creating the bounded ceremony-confusion hazard documented in
`f-b9ff071-webauthn-cross-origin-policy`.

## Falsification attempt and counterevidence

I tested a public-key substitution with an internally consistent attacker assertion: the unchanged service signature
refuses it, so the anchor addresses the row's load-bearing attack. I tested whether exact origin/RP-ID checks also
reject cross-origin framing; W3C distinguishes the caller origin from `crossOrigin`/`topOrigin`, and a valid signed
assertion from the app origin inside a delegated iframe passes the project code. I tested whether the default
Permissions Policy makes that impossible; it blocks the default case but WebAuthn §5.9 permits explicit delegation,
so the relying-party policy check remains owed.

## Nuance preservation

The commit carefully preserves three distinctions: no secret to stretch is not the same argument as high entropy;
slot proof is not account authentication; and a service-signed public key is stronger than the default local custody
beside it without expanding that custody claim. The one missing nuance is the top-level embedding context in the
otherwise detailed WebAuthn verification order.

## Verdict

Supported with qualifications. The asymmetric credential and service-signed slot binding are well matched to the
original offline-verifier threat, and the substitution negative is persuasive. Browser-level conformance,
authenticator availability, deployment framing policy, and the missing WebAuthn cross-origin check remain necessary
before the selection is implementation-complete.
