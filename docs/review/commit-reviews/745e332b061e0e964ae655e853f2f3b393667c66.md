## Construction and state-machine effect

### Accepted state and retention

For credential `c`, the client persists only the last accepted `(seq, link)`. It admits the next gap-free run by
checking envelope authenticity, exact successor positions, links recomputed from its held link, and one signed head
against the recomputed terminal link. A checkpoint's accepted-head vector is the same chain state at an earlier
position, so replay from genesis and replay from that baseline converge. Content commits before the encrypted heads
record; a crash therefore causes harmless idempotent re-delivery rather than an unrecoverable applied-content hole.

Own outbound envelopes remain through the second-newest admitted checkpoint, because fallback to that checkpoint
requires each source device to re-envelop its own suffix from the baseline it actually applied. Silence after an
outbound position never licenses re-mint; only a definite refusal does, because a second link at a possibly accepted
position is indistinguishable from credential compromise.

### Package state

One manifest/parts format represents never-established, live, and retired lineage states. The package carries a
checkpoint, epochs, retained suffix, generation wraps, live/terminal head, and recovery public key plus code-sealed
private key. The selected root anchor is
`HPKE.Seal(R_pub, info(workspace,lineage,auth_root,generation), K_g)`. This binds the value used by one ciphertext,
but HPKE base mode lets anyone holding `R_pub` produce a new ciphertext under any chosen `info`.

## Assumptions and guarantee boundaries

- Row 6's chain is cryptographic within one view; a service can maintain split views until they meet.
- The local heads record is rollbackable to an earlier valid ciphertext; exploitation needs an alternate
  service-signed link and therefore falls inside the already-declared equivocation bound.
- Retention depends on two admitted checkpoints and their suffixes actually remaining available; cadence remains a
  future service/measurement choice.
- Definite refusal needs authoritative semantics; silence and timeout are explicitly not refusal.
- Package signatures authenticate only beneath the package-supplied root. The recovery code authenticates the
  sealed `R_priv`, not values merely encrypted to its public counterpart.
- Never-established archives intentionally lack external identity authenticity.

## Evidence and oracle independence

The antireplay generator checks replay equivalence, 13 negatives, three demonstrations, record AAD, and the
content-before-mark invariant using project-owned composition code. The package generator first reproduces RFC 9180
A.1.1, then checks three states and 15 negatives. In a disposable exact-commit snapshot on 2026-08-21, both
`--check` commands passed.

The external RFC vector supports the HPKE encoding implementation, not the application's trust theorem. The
`substituted-trust-root` negative reopens the original generation wrap using changed `info`; it does not let the
attacker create a new wrap. Since RFC 9180 base mode explicitly encrypts to a recipient public key without sender
authentication, producer and checker share the wrong application model for the decisive negative.

## Consequences and residual failures

The mark construction reduces persistent state without weakening a single-view accepted-chain check, and its
write-order/retention corrections prevent concrete crash and fallback loss. Gaps and missing heads remain
availability failures, while service split view remains detectable only when views meet.

The package root anchor fails its stated attacker. A party able to rewrite a package can retain genuine `R_pub` and
the code-sealed genuine `R_priv`, choose an attacker root and content key, HPKE-seal that key to genuine `R_pub`
under `info(attacker_root)`, and rebuild the checkpoint, epochs, credentials, attribution claims, head and manifest
under the attacker root. The user's code opens the unchanged genuine `R_priv`, which then opens the attacker-created
wrap. This permits complete content/attribution substitution during total-loss restore or migration.

## Falsification attempt and counterevidence

- I replayed the exact committed row-6 and row-10 checkers; all published positives and negatives passed.
- I challenged whether a log is needed to reject a second link below or at the mark. Exact-successor arithmetic
  rejects below-mark input; a head checked against the client's recomputed link rejects the at-mark fork. No extra
  history is needed.
- I challenged second-newest retention with newest-checkpoint loss; a device trimmed to newest cannot supply its
  suffix from fallback, so the deeper floor is necessary.
- I challenged package root substitution by retaining the real recovery keypair instead of substituting it. The
  package itself exposes `R_pub`; RFC 9180 base-mode sealing needs only that public key. Recomputing both `info` and
  ciphertext defeats the published negative and leaves the user's code-sealed `R_priv` usable.
- I checked whether the manifest or epoch signatures rescue the anchor. They do not: every verification key is
  resolved beneath the substituted root, which the selection itself identifies as the reason an anchor is needed.

## Nuance preservation

Row 6 preserves and improves the original distinctions among accepted evidence, replay mark, checkpoint baseline,
own-envelope retention, service suffix retention, and split-view residual. Row 10 correctly unifies artifact states
and keeps Local archives' weaker meaning explicit, but mistakes context binding inside attacker-created public-key
ciphertext for authentication of the context itself.

## Verdict

`reopen`: the accepted-state mark and retention half is supported with stated split-view/availability bounds, but
row 10's load-bearing trust-root anchor is invalid under the exact package-writer threat it claims to stop. The
package construction cannot remain selected without an anchor authenticated by user-held secret state.
