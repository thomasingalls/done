## Change seen while moving backward

Returning to the parent removes the purpose-built RustCrypto XChaCha20-Poly1305 WASM crate, its 6,465-byte
base64-inlined artifact and synchronous wrapper, build/size/verification tools, full-write and cipher benchmark
paths, and the paired Pixel 9a results. The parent retains the XChaCha construction and a measured 4 kB breach;
this commit supplies an implementation whose recorded 240 µs p95 full write is below the 1 ms threshold.

## Original-contract trace

This directly answers original claim `OC-025`: preserve the synchronous crash journal, use a reviewed synchronous
AEAD and domain-separated journal subkey, survive page kill without counter state, and meet the low-end latency
budget. It does not answer the still-open payload qualifier or integrated crash/replay behavior.

## Construction and state-machine effect

The cryptographic carrier does not change: 32-byte journal subkey, random 24-byte nonce, AAD, and
XChaCha20-Poly1305 ciphertext plus 16-byte tag. The implementation moves sealing from pure JavaScript to a
`no_std`, allocator-free WASM instance with fixed buffers and one synchronous `seal` call. The module is decoded,
compiled, and instantiated during bundle evaluation, so the intended startup state has no post-evaluation interval
in which edits can be accepted before a seal exists. The commit explicitly does not integrate this path into
`src/`; Stage 1 still owes startup, write, replay, error handling, and migration from `1:` journal entries.

## Assumptions and guarantee boundaries

- Cryptographic: correct 32-byte key, fresh 24-byte nonce, AAD, and plaintext yield the selected construction.
- Operational: caller-generated nonce freshness and exact key/nonce widths remain outside the Rust length guard.
- Platform: synchronous WebAssembly compilation and SIMD are hard support-floor requirements; there is no fallback.
- Measurement: 35/65/240 µs p95 applies to the recorded Pixel 9a session and three payloads, not all low-end devices
  or unbounded updates.
- Assurance: the committed artifact has a direct external KAT plus project composition vectors, but the selected
  crate version and compiled artifact are not themselves covered by the 2019 source audit.
- Product/integration: no application or relay path imports the module at this commit or at the pinned tip.

## Evidence and oracle independence

`scripts/check-wasm-seal.mjs` runs the committed generated module against the external draft A.3.1 KAT, four
project composition vectors, oversize AAD/plaintext refusal, and maximum accepted lengths. This is meaningfully
stronger than a generator checking its own bytes: the KAT can catch shared primitive mistakes, while the composition
vectors bind project framing. It still samples behavior rather than proving all inputs or source-to-binary identity.

In a disposable exact-commit snapshot on 2026-08-21, Node `v26.7.0` reported all eight checks passing. With
`rustc 1.100.0-nightly (f7d782a3b 2026-08-19)`, `build-wasm-seal.mjs --check` regenerated the same 6,465 bytes.
This is positive counterevidence to artifact staleness in that environment. The repository does not pin the Rust
toolchain, and `pnpm check` runs `wasm:verify` but not the separately defined `wasm:stale`, so this is not a durable
hermetic source-to-artifact proof.

## Consequences and residual failures

The measured implementation closes the recorded 4 kB performance breach without changing on-wire bytes and is
smaller than the replaced JavaScript library in the recorded bundler method. A missing SIMD capability fails at
bundle evaluation, oversize AAD/plaintext refuses, and a trap prevents a silently malformed record. Residuals are:
wrong-sized key/nonce inputs are silently accepted; integration and crash semantics are absent; large payload policy
is open; measurements are device/session-specific; and the audit/review criterion is not closed by KAT agreement.

## Falsification attempt and counterevidence

- I reran the exact committed checker: eight checks passed, including the external KAT and both length boundaries.
- I regenerated the exact module from the exact snapshot: it matched in the available 2026-08-19 nightly toolchain.
- I searched `src/` and `relay/` at this commit and the pinned tip: no module import survived, confirming the commit's
  own non-integration qualification.
- I challenged the wrapper's only documented failure path with empty key and nonce values. Both were accepted. An
  empty key reused the prior instance's 32 key bytes, and an empty nonce under the same key reproduced the prior
  ciphertext and tag, demonstrating the nonce-reuse hazard in `f-9b49b74-wasm-glue-key-nonce-lengths`.
- I checked the review provenance: NCC's engagement occurred in December 2019; RustCrypto records `0.10.1` as an
  August 2022 release. Thus the audit is real but not an audit of the selected version.

## Nuance preservation

The commit carefully preserves the payload qualifier, integration absence, SIMD hard floor, and the open question
of whether a compiled artifact inherits source review. It loses one nuance present in the earlier noble assessment:
the source audit's version gap. It also describes the module's length guard as the only failure path while the
JavaScript glue silently permits invalid key/nonce widths.

## Verdict

`supported-with-qualifications`: the committed artifact implements the selected bytes, the independent KAT and
project vectors pass, exact regeneration succeeds in the recorded environment, and the paired measurement supports
the bounded 4 kB performance conclusion. This does not close integrated crash safety, all-device performance,
source/artifact review, or the two candidate concerns below.
