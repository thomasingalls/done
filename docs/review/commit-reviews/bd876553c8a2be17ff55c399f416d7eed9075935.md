# Commit `bd87655` — `Set the browser support floor, and state what Baseline cannot`

## Change seen while moving backward

Returning to the parent removes the project's first explicit browser policy and restores two open questions:
whether WebCrypto Ed25519 needs a fallback and what optional WebAuthn PRF availability means. This commit selects
Baseline newly available for general platform features, records capability-specific evidence where Baseline is
too coarse, accepts Ed25519 without a fallback, and preserves generated-code recovery as the root so missing PRF
costs convenience rather than access.

## Original-contract trace

This advances `OC-004`, `OC-042`, `OC-045`, `OC-050`, and `OC-064`: portability and optional device-bound
enhancement need a declared platform boundary, while the synchronous journal still owes evidence on low-end
hardware. It also closes the support-floor half of row 1's explicit Stage-4 debt without pretending that prose
is a conformance test.

## Construction and state-machine effect

No byte construction or persistent state changes. The policy changes which platform states are supported:
ordinary features enter scope when all core browsers' current stable releases support them; Ed25519 is handled
as an algorithm-specific exception to Baseline's aggregate WebCrypto feature; PRF remains optional across an
OS/browser/authenticator matrix. Because the generated code is the mandatory root, absence of PRF never changes
the recovery or local-unlock security bar.

The selected suite also contains HPKE base mode with DHKEM(X25519), whose WebCrypto availability is load-bearing
for Stage 4. The contemporaneous row-14 record explicitly identified X25519 as the same unresolved support-floor
class, but §10.11 calls Ed25519 and PRF the whole capability-specific list and omits X25519.

## Assumptions and guarantee boundaries

- Baseline is an interoperability/support policy. It says that a web feature works across core browser releases;
  it does not specify CPU, storage, memory pressure, or latency characteristics of the devices running them.
- Ed25519 compatibility is a dated platform statement, not a build guarantee; the commit correctly leaves the
  Stage-4 conformance test open.
- PRF availability is operational and authenticator-dependent, not a cryptographic fallback condition. The
  construction safely treats it as absent by default.
- The current-stable floor moves. Evidence dates and later revalidation are therefore part of the policy.
- X25519 support remains an unstated platform assumption even though HPKE is a selected suite component.

## Evidence and oracle independence

The Ed25519 version table matches independent browser-compatibility data and release notes, and the aggregate
Baseline limitation is real: WebCrypto feature status is not per algorithm. The PRF matrix is directionally
supported by the WebAuthn capability model and platform/vendor documentation; runtime capability detection is
still required because version alone cannot decide authenticator support.

The sources do not support the separate inference that a current browser creates a lower bound on device
performance. Nor does the commit record an X25519 compatibility table, conformance vector, or fallback despite
the row-14 record already naming that question. The later suite generator still says HPKE has no vector.

## Downstream propagation

TRD §§10.11 and 13.10, row 1, row 13, development/test planning, and later stage gates inherit the Baseline
policy. The real-device journal evidence uses the policy as the stated substitute for the unavailable named
low-end handset. Stage-4 mutation signatures inherit the dated Ed25519 conclusion; HPKE recovery and reader-wrap
paths inherit the unrecorded X25519 assumption.

## Consequences and residual failures

The policy is useful and the optional-PRF construction is robust: unsupported PRF cannot lock out a user or
silently weaken the mandatory generated-code path. The Ed25519 claim is appropriately bounded until tested.

Two residual failures survive. First, browser interoperability cannot close or reinterpret a hardware p95 budget;
the journal still needs a declared device population or actual lower-bound device evidence. Second, the supposedly
complete capability list omits X25519, so the supported Stage-4 HPKE state is not established by this commit.

## Falsification attempt and counterevidence

- I compared the stated Baseline rule with its primary definition. Newly available means interoperable across the
  core browser set; nothing in that definition constrains the hardware that may run a supported browser.
- I checked the Ed25519 versions against compatibility data and browser release notes; the table is consistent.
- I tried to turn PRF into a mandatory-floor failure. The construction defeats it because generated code remains
  mandatory and PRF only adds another seal.
- I enumerated every selected platform primitive. AES-GCM, HKDF, SHA-256, Ed25519, and PRF are discussed, but
  WebCrypto X25519 is absent even though row 14 flags it and row 1 selects it for HPKE.

## Nuance preservation

The commit is unusually explicit about where Baseline stops, that Ed25519 remains untested, that PRF is a matrix,
and that the support floor moves. That nuance is faithfully propagated. The two departures are narrower: the
performance-floor paragraph attributes a property Baseline does not carry, and “whole current list” drops the
already-recorded X25519 question.

## Verdict

`supported-with-qualifications`: the general floor, Ed25519 evidence, and optional-PRF consequence are sound and
materially improve the contract. Baseline cannot substitute for a low-end performance population, and the
capability-specific inventory is incomplete without X25519.

## Findings and unresolved checks

- `f-bd87655-baseline-not-performance-floor` — browser feature interoperability does not bound device latency.
- `f-bd87655-x25519-support-floor-omitted` — the support inventory omits a load-bearing HPKE primitive.
- Stage 4 should test Ed25519 and X25519/HPKE on the then-current declared floor and exercise PRF absence as the
  default path.
