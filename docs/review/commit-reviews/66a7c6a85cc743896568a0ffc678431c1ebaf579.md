## Change seen while moving backward

Returning to the parent removes the reproducible browser microbenchmark and restores three Node-only
cipher figures with two explicit caveats. This commit adds four measured levels—plaintext storage,
seal, seal plus base64/framing, and sealed storage—at three payloads on desktop and a 4x CPU-throttled
desktop profile. It records batch means, conditionally asserts honest unthrottled tails, and says a real
device is still required for the low-end p95.

## Original-contract trace

This advances `OC-025`, `OC-050`, `OC-051`, and `OC-064`: the journal budget is on the synchronous
operation that blocks handler return, so selection evidence must include nonce generation, seal,
framing/base64, and durable storage rather than primitive timing alone. It arrives before Stage 1,
when evidence can still change the implementation choice.

## Construction and state-machine effect

No application construction changes. The test bundles the row-2 specification rather than importing
unbuilt Stage-1 code, refuses measurement unless it reproduces the keystroke vector, and creates a fresh
24-byte nonce inside each sealed operation. Dynamic batch sizing pushes means above clock granularity;
4,000 individually timed writes supply a p95 only when CPU throttling is absent.

The four labels are best read as one plaintext baseline plus three cumulative encrypted-path levels,
not one strictly cumulative chain: `plaintext` performs base64 plus `setItem`, while `seal` starts a
separate encrypted chain. The difference between stored encrypted and stored plaintext estimates added
encryption/framing cost.

## Assumptions and guarantee boundaries

- Desktop and a CDP 4x stall profile are not low-end hardware. The throttled batch mean is useful for
  component sensitivity but its per-operation tail is explicitly unattributable.
- A batch median/mean far below 1 ms is not a proof that p95 is below 1 ms; the performance prose's
  “budget holds by twenty times” is an inference the same commit later limits as unmeasured.
- The minimal isolated page excludes application contention and integrated crash ordering.
- The benchmark overwrites one warmed fixed key and precomputes a fixed AAD, unlike immutable per-entry
  production journal appends.
- The pre-measurement project vector checks exact selected bytes for one input, not the performance
  representativeness of the storage workload.

## Evidence and oracle independence

The harness is reproducible in shape: exact code, locked dependencies, three payloads, dynamic batch rule,
sample counts, clock/isolation assertions, and expected vector survive. The vector is generated by the same
project model, though its primitive KAT supplies an external algorithm oracle. Recorded result samples go
to ignored `test-results/latency.jsonl`; only summary tables survive.

This workspace lacks the locked `@noble/ciphers` installation and could not rerun the exact historical
browser suite. The published arithmetic is internally consistent: on the throttled profile 48.2/9.4 is
about 5.1, and at 4 kB the 104.3-microsecond framed-minus-seal term is comparable to the
125.9-microsecond seal. Those are component means, not the required device p95.

## Downstream propagation

`3670591` reuses the module and constants on a Pixel 9a, disproves the throttle extrapolation, and supplies
the actual p95. `138a5f8` exports the same measurement routine for cipher comparison. `9b49b74` later

## Consequences and residual failures

The benchmark correctly reveals that base64/storage are material, that desktop ratios are not a safe
mobile model, and that primitive timing alone cannot close the journal budget. It does not yet answer the
budget's named statistic. Its fixed-slot workload also under-specifies the production write, so even the
later hardware p95 needs a production-shaped append check.

## Falsification attempt and counterevidence

- I traced the vector gate, fresh nonce allocation, four operation paths, clock probe, warm-up, dynamic
  batch size, and conditional p95 assertion; each matches the stated method.
- I challenged the “whole write” label against TRD §6.1. The test uses one pre-warmed slot for every
  operation rather than fresh immutable keys that accumulate until batch commit.
- I checked the mean/p95 distinction. The test never asserts a throttled p95, yet the ledger briefly says
  the mean proves the p95 budget; the same section correctly calls that statistic unmeasured.
- I tested the claimed base64 dominance arithmetically. At 4 kB it is comparable to the JS seal in these
  runs, while at common size it is not the dominant term.

## Nuance preservation

The commit improves nuance by separating primitive, framing, storage, mean, tail, desktop, throttle,
and hardware. It explicitly refuses to substitute a throttled tail for the budget's p95. The headline
“budget holds” sentence overreaches that distinction, and the fixed-slot workload remains unnamed.

## Verdict

`supported-with-qualifications`: measuring the full component chain is the right correction and the exact
harness records useful means. It does not close the low-end p95 and does not faithfully model immutable
journal storage; the following hardware commit supersedes the former limitation, not the latter.
