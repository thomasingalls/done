### Accepted-state theorem and fork bound

The forward construction is coherent when its guarantees are kept within one client view. An
author-signed envelope authenticates a non-circular AAD header and signature-reachable nonce and
ciphertext digest. Each credential owns one sequence, and a client recomputes the exact successor
link from its held `(seq, link)` rather than trusting a service-reported position. It admits a
gap-free run only when a service-signed head names the recomputed terminal link. A checkpoint's
accepted-head vector is the same state at an earlier position, so replay from genesis and replay
from that baseline converge without retaining a separate acceptance log.

The local heads record is rollbackable, but a rollback is useful only if the service can supply a
different valid signed link; that is the already-declared equivocation case. A service can maintain
split views until they meet, at which point conflicting accepted heads expose the fork. The theorem
therefore establishes per-view cryptographic consistency and eventual fork evidence, not a global
single-copy order or fork prevention.

Content commits before the encrypted accepted-head mark. A crash can consequently cause harmless
idempotent redelivery rather than an accepted-content hole. Silence never authorizes re-minting at
the same position; only a definite refusal may do so. Each device must retain its own suffix through
the second-newest admitted checkpoint, because losing the newest checkpoint otherwise leaves no
source for replay from the fallback baseline.

### Retention, attribution, and trust-root seams

The row-6 mark, write ordering, and second-newest retention are mutually necessary and supported.
Row 7's checkpoint evidence, however, signs independently chosen snapshot, state-vector,
delete-set, and accepted-head constants; it never derives their semantic relationship from real
Yjs state. The construction may be implementable, but the current oracle does not demonstrate the
coverage needed to trim old content and keys safely.

The attribution tuple prevents another credential from signing an unchanged source tuple, but a
mutable CRDT map cannot make a value write-once to a fresh restorer. An admitted credential can
replace the whole tuple with a self-consistent claim naming itself; after compaction the record
verifies without evidence of the original creation event. This reopens row 8.

Most importantly, row 10 does not authenticate the historical authorization root. HPKE base mode
lets any package writer seal a new attacker-chosen content key to the genuine public recovery key
while choosing matching `info` containing an attacker root. Keeping the genuine code-sealed private
key then makes the attacker's new wrap open successfully, and all other signatures resolve beneath
the substituted root. The published negative only changes `info` on an old ciphertext and therefore
tests context binding, not sender or root authenticity. Package restore, migration, and terminal
archive guarantees that depend on this anchor are reopened.

### WASM evidence and later-only conclusions

The journal seal's committed bytes pass an external XChaCha KAT, four project composition vectors,
and length-boundary checks. In an exact-commit disposable archive, all eight checks passed under
Node `v26.7.0`, and the 6,465-byte generated artifact regenerated exactly with
`rustc 1.100.0-nightly (2026-08-19)`. The recorded Pixel 9a 4 kB full-write p95 is 240 microseconds
against a 1 ms threshold. That is bounded positive evidence, not an all-device result: the Rust
toolchain is unpinned, the ordinary aggregate check does not run the staleness check, and neither
the historical commit nor pinned tip integrates the module into application or relay paths.

The wrapper validates AAD/plaintext maxima but not the fixed 32-byte key and 24-byte nonce. Because
the WASM instance reuses fixed buffers, empty inputs can retain prior bytes; in the exact artifact an
empty nonce under an unchanged key reproduced the prior ciphertext/tag. The external RustCrypto
audit is real, but its December 2019 engagement predates selected version `0.10.1` (August 2022), so
source-delta and compiled-artifact review remain distinct assurance scopes.

Several claims become true only with later commits in this batch. `a073574`'s enrollment transcript
does not bind the current epoch until `992bc91`; `992bc91`'s safe re-mint statement needs
`745e332`'s definite-refusal rule; row-6 retention depends on row-7 checkpoints and row-8
attribution, while row-10 portability consumes all three and therefore inherits their reopened
seams. `9b49b74` supplies the implementation evidence for a construction selected earlier; B-03
still owns the earlier AAD and performance evidence on which that selection was based.

## Affirmative conclusions

- A single persisted `(seq, link)` per credential is sufficient accepted-chain state within one
  view; no acceptance log is needed to reject an alternate link at or below the mark.
- The source-envelope field split is non-circular and reaches all security-relevant bytes through
  AAD or the author signature. A single client-owned sequence and client nonce are necessary and
  coherently selected.
- Content-before-mark ordering, definite-refusal-only re-mint, and second-newest own-envelope
  retention close distinct crash, fork, and fallback-loss cases without claiming service liveness.
- Accepted-chain finalization is sound within the stated split-view bound. Enrollment's committed
  nonces, five-symbol typed SAS, and QR-as-accelerator separation are internally coherent; the
  later epoch-head amendment closes transcript freshness.
- The purpose-built WASM artifact implements the selected XChaCha bytes, passes an independent KAT,
  regenerates exactly in the tested toolchain, and supports the recorded bounded 4 kB latency claim.
- `130757d` is exactly traceability-only: two branch-name placeholders become the immediate parent
  SHA with no substantive change.
