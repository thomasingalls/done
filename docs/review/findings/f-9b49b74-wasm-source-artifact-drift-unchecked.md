# `The normal check can verify a stale WASM blob while its reviewed Rust source has changed`

## Affected requirement or guarantee

TRD section 10.9 treats the checked-in `seal.generated.ts` module as an auditable, deterministic implementation
of the reviewed Rust source, and row 1 relies on that module's known-answer and boundary evidence. The evidence
must therefore bind the source under review to the exact bytes that the product imports.

## Original source

At `c6116669030eedeea3d599bca0da3547114e6930`, row 1 is open and there is no Rust/WASM implementation or
source-to-artifact assurance claim.

## End-state source

At `9edd9300adebcec3abd2234c946f1dcccdc17eef`, `package.json` includes `wasm:verify` in the normal `check`
script, but not `wasm:stale`. `scripts/check-wasm-seal.mjs` instantiates and tests the already-generated bytes;
only `scripts/build-wasm-seal.mjs --check` rebuilds from `wasm/seal/src/lib.rs` and compares the artifact. The
Rust toolchain is also not pinned, so the latter comparison is not yet a reproducible source-to-binary attestation.

## First introduction and propagation

`9b49b743cb03cb8827682d79fc66405f458cf29b` introduces the Rust source, generated blob, verifier, builder,
and split scripts. Later commits preserve the split through the pinned tip: routine `pnpm check` validates the
blob's behavior while the source/artifact freshness check remains opt-in.

## Reachable consequence

A source-only security fix, limit change, or review edit can leave the shipping blob unchanged while all normal
checks pass. Conversely, reviewers can audit source that is not the product implementation. The current blob still
passes the external XChaCha20-Poly1305 KAT and project composition tests, so this is an assurance and release-drift
hazard rather than evidence of a present cryptographic defect.

## Supporting evidence

In a disposable archive of exact tip `9edd930`, I changed only `MAX_AAD` in `wasm/seal/src/lib.rs` from `4096`
to `2048`. `node scripts/check-wasm-seal.mjs` still passed all eight checks because it exercised the old embedded
blob. `node scripts/build-wasm-seal.mjs --check` then reported `seal.generated.ts is stale`. This is a direct
counterexample to treating the normal check as a source-to-artifact guard.

## Counterevidence and disconfirmation attempt

I tested whether the KAT verifier rebuilt the module implicitly; it does not. I also checked whether another command
inside `check` invoked the stale check; none does. The explicit `wasm:stale` command is useful and the generated
file records a toolchain string, but an optional command plus an unpinned compiler does not make routine verification
bind source to artifact.

## Validation procedure

1. Archive exact tip and install the already-declared toolchain/dependencies.
2. Change a behaviorally meaningful Rust constant without rebuilding `seal.generated.ts`.
3. Run `node scripts/check-wasm-seal.mjs`; observe that it tests and accepts the old blob.
4. Run `node scripts/build-wasm-seal.mjs --check`; observe the stale-artifact failure.
5. Add the freshness check to the required review/CI path and pin or attest the source, toolchain, and output hashes.

## Disposition

Validated by `V-01`. Make source-to-artifact freshness mandatory in the normal check and add reproducible or
attested toolchain provenance. Preserve `wasm:verify` as an independent behavioral check; it catches a different
class of failure.
