see, and every device holding `K_g` used to derive the identical subkey while each device's counter saw only
its own share. §3's bound and §4's scope rule are rewritten below; `wrong-store-subkey` is the derivation's
published negative.

## The selection

```
Content record  (IndexedDB, structured clone)

  StoredRecord = { v: 1, gen, seq,
                   kind: 'update' | 'state' | 'heads' | 'outbound',
                   nonce: Uint8Array(12), ct: Uint8Array }   // ct carries the 16-byte tag

                   'heads'    row 6's anti-replay mark, in its own object store
                   'outbound' row 4's minted envelopes, in its own object store

  K_store = HKDF-SHA256(ikm = K_g, salt = "",
                        info = LP("done/store/v1") || LP(workspace_id)
                               || LP(store_id), L = 32)

  store_id  minted from local randomness at store creation, beside the
            SeqCounter it names; cleartext in the store's metadata.
            One key per counter -- see §3 and §4 (P-3, S0-3).

  AAD     = LP("done/store/v1") || LP(principal_id) || LP(workspace_id)
            || LP(store_id) || LP(dec v) || LP(dec gen) || LP(dec seq)
            || LP(kind)

  Nonce   12 bytes from crypto.getRandomValues() per record, under a
          2^32-per-(store, generation) budget the SeqCounter's
          reserved[gen] counts. NOT `seq`, which does not reset -- see §3
          (S0-3).

  seq     RESERVED before encryption, per batch, in one IndexedDB
          transaction that also adds k to reserved[gen]. It is in the AAD,
          so it is fixed before the record exists and two tabs would
          otherwise choose the same one (S0-3).

Local key envelope  (the key store, structured clone)

  KeyEnvelope = { v: 1, gen, nonce: Uint8Array(12), ct: Uint8Array }
                ct = AES-256-GCM(L_lock; plaintext = K_g, 32 bytes) // L_local only in legacy fixtures

  AAD     = LP("done/keyenv/v1") || LP(principal_id) || LP(workspace_id)
            || LP(dec v) || LP(dec gen) || LP(purpose)      // purpose = "content-key"

Both      AES-256-GCM via WebCrypto (suite 1, row 1).
          LP(s) = uint16be(byteLength(utf8 s)) || utf8 s
```

Everything below is why, and what it cost.

---

## 1. Two formats, one set of binding rules

Row 3 covers both because they are the same construction twice, one level apart: the envelope holds the key
that derives the subkey that opens the records. §6.1's start-up order makes the dependency literal —
`open key store → unseal K_g → derive subkeys → replay journal → load content records` — so **every content
record is unreadable until the envelope opens**, and a format decision that is right for one and wrong for the
other has no natural place to be caught.

The shared rules, all three of them inherited from row 2 rather than reinvented:

1. **`LP()` length-prefixed AAD fields, never delimiter-joined.** A delimiter-joined encoding is not
   injective — a workspace id containing the delimiter shifts every field after it, and two different contexts
   can encode to identical bytes. Injectivity is the only property AAD needs. It matters more here than in the
   journal: this format has **seven** cleartext fields to bind rather than one, so an ambiguous encoding has
   proportionally more room to do damage.
2. **Any cleartext field a reader trusts is authenticated.**
3. **A binding that costs nothing and removes a class of confusion is taken**, rather than being argued down
   to "probably harmless".

---

## 2. Every cleartext field is in the AAD, and one of them can delete the store

IndexedDB holds a **structured clone**, not a byte string. That is the substantive difference from the
journal, and it cuts both ways: no base64, so no expansion — but `v`, `gen`, `seq` and `kind` are ordinary
editable JavaScript properties to anyone who can reach the profile, and the load path trusts all four.

| Field  | What the load path does with it              | What an unbound version would allow                                                       |
| ------ | -------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `v`    | Selects the suite (row 1)                    | Point a record at a different suite — the downgrade surface row 1 §4 exists to remove     |
| `gen`  | Selects which `K_g` to derive from           | Claim a generation the record was not sealed under                                        |
| `seq`  | Orders the trim                              | Renumber a record so trim keeps or drops the wrong one                                    |
| `kind` | Decides whether a record supersedes the rest | **Mislabel an ordinary update as replacement state; authentication must reject it, and kind alone proves no deletion coverage** |

**`kind` is the sharp one and it is worth being explicit about.** A `state` record is the collapsed whole
document; trim separately proves exact authenticated record coverage before deletion. So a `kind` an attacker can edit is not an integrity
nuisance, it is a way to make the store delete its own history using the store's own maintenance path. One
byte of AAD closes it.

**`principal_id` is bound, and the reason is ordinary rather than adversarial.** PRD §6.7's forcing case is
not the shared laptop: every synced user has a Local workspace before they have an account, so a device that
signs in holds an anonymous workspace **and** an account workspace — _"two principals on one browser profile,
with no second human anywhere near it. That is the ordinary path."_ Two stores, two principals, one profile,
routinely. Binding the principal means a record that ends up in the wrong one fails to open instead of being
absorbed. §6.1's _must not happen_ list already forbids a provider writing across that boundary; this makes
the violation non-silent.

**The database name is not bound, and does not need to be.** §6.5 derives it from _(principal, workspace)_,
so binding the pair binds the name — and the pair is what a reviewer can read.

## 3. The nonce discipline, and why its shape differs from row 2

AES-256-GCM takes a 96-bit nonce. **12 random bytes per record, from `crypto.getRandomValues()`.** This path
is asynchronous and has no crash constraint, so none of row 2's contortions apply — but the safety argument
has a different shape here, and the difference is exactly what a reviewer should be pointed at.

Row 2 rejected a 96-bit nonce for the journal in strong terms: the guarantee "would become a claim about
application behaviour that a later change can silently invalidate." **That objection applies here on its face,
and it is answered rather than waived.**

**The bound.** NIST SP 800-38D §8.3 limits **a key** to 2^32 invocations when nonces are random, which holds
the collision probability at or below 2^-32. `K_store` is per **store instance and generation**, so the budget
is per (store, generation) — and the store term is what makes the bound true rather than merely stated (`P-3`,
ratified 2026-08-28). The counter below is one `SeqCounter` per store, and IndexedDB is device-local by
construction, so a subkey derived from `K_g` and the workspace alone would be the identical key on every device
holding `K_g`: `D` stores each granted 2^32 gives `q = D·2^32`, collision probability ≈ `D²·2^-33` — above the
claimed 2^-32 for every `D ≥ 2`, visible to no per-store comparison. Binding the `store_id` in the derivation
makes the sum over devices a sum over distinct keys, so `reserved[gen]` counts every invocation of the key it
bounds and the one comparison is again the whole enforcement.

**What makes it unconditional here is that the condition is checkable, and row 2's was not.** The journal had
no durable counter by definition — that was the whole premise of the row — so its safety would have rested on
"this journal never holds many entries", a claim about behaviour with no enforcement point anywhere in the
code. The content store already carries `seq`, monotonic per store, in every record. **The check is one comparison** — a store whose next write would be the 2^32nd invocation under the current
generation rotates before that write rather than after it, and equality is the first disallowed value.

**But the field it reads is not `seq`, and this row said it was** (`S0-3`,
`f-dbfd01f-record-nonce-ceiling-omitted`). The sentence that used to stand here — _`seq` counts every record
ever written while the budget only counts records under the current generation, so using it is conservative in
the safe direction_ — is true exactly until the first rotation, and false forever afterwards: `seq` does not
reset, the budget does, so a literal `seq ≥ 2^32` test refuses every write for the rest of the store's life.
Conservative in the safe direction is what it looks like from generation one.

**The count is `reserved[gen]`, and the reason is stronger than the arithmetic.** NIST SP 800-38D bounds
**invocations**, and an encryption abandoned before commit is an invocation. A count recovered from committed
records cannot see it. Reserving before encrypting counts it by construction: **the gap a crash leaves is the
record of an invocation that happened.**

**And `seq` is reserved rather than read, which this row needed and did not select** (`S0-3`,
`f-3bea0e6-store-sequence-allocation-undefined`). §2 above rejects a derived counter nonce because _two tabs on
one origin can open the same store, and both would compute the same next counter_ — and then leaves `seq`
itself to the same two tabs. It is inside the AAD, so it is fixed before encryption and cannot come from an
auto-increment key. One durable `SeqCounter` per _(principal, workspace)_ grants a whole batch's range in one
transaction, which is what serializes them, and adds `k` to `reserved[gen]` in the same transaction.

**Per batch, exactly sized**, which is neither of the two options the review offered: the adapter already
writes a batch in one transaction and already knows how many sequences it needs, so a transaction per record
would be one per keystroke and a per-tab lease introduces ranges that can be abandoned in part. **And what it gives the
trimmer is uniqueness rather than a watermark** — a trim deletes what its state record covered, and *what it
covered* is expressible only because one `seq` is issued once. Two tabs both writing at `max + 1` put two
records at one number, and no rule stated over numbers can then separate them. The race is upstream of the
trim's rule, in the numbering.

**One consequence this pins that §6.1 left open: `seq` does not reset at trim.** §6.1 specifies the trim's
crash-safe ordering but says nothing about numbering, and a `seq` that restarted after each trim would be
equally serviceable for ordering — and would destroy its usefulness as the nonce budget. It continues from the
surviving state record. That is a small thing to get wrong and an expensive one to discover.

**A rejected alternative, for completeness.** A deterministic counter-derived nonce would remove the birthday
argument entirely, and the store _does_ have durable state, so row 2's objection does not transfer. It is
declined because two tabs on one origin can open the same store, and both would compute the same next counter
from the same durable maximum. Random nonces have no such path. The concurrency assumption a counter needs is
precisely the kind of application-behaviour claim this section is trying not to depend on.

## 4. Derivation names the key's scope; AAD names the record's home

`K_store` is derived from `K_g` under the workspace and the store instance, with the same KDF and label
encoding as row 2's `K_journal` — §13.2's separation stays a property of the labels a reviewer can read, and
the extra `info` term is a scope term rather than a separation one.

The rule survives corrected, not repealed (`P-3`, ratified 2026-08-28):

> **Derivation names what the key is scoped to — and the budget is what fixes the scope: a key's scope can be
> no wider than the state that counts its invocations. AAD names where the record lives.**

The earlier premise here ran the inference backwards: it read the scope off `K_g` — *a content key for one
workspace generation, so its subkeys are workspace-scoped by construction* — and concluded that adding anything
narrower *would claim a scope the key does not have*. The budget decides, not the parent key: §3's bound is
enforced by one `SeqCounter` per store, so the key that bound protects must be per store, and the `store_id`
minted beside the counter is exactly the identity that makes them one-to-one. It exists at creation for every
store — the anonymous Local workspace included — within an unrewound, unbranched history (SC-09), which is the floor the
ratifier fixed. The principal still appears in the AAD but **not** in the derivation: the *record* lives in a
store keyed by _(principal, workspace)_ per §6.5, and that is what its AAD should say, while the store's own
identity now travels in both — so a record that lands in the wrong store fails **at the key as well as the
AAD**, defense in depth for §6.7's two-principals-one-profile case §2 argues from. Row 2's
`journal_storage_key` binding is the same rule applied to the journal's own home.

**The label namespace has room for the fourth subkey.** §13.2 anticipates a search-index subkey; `done/index/v1`
is reserved by construction and not selected — whether a persistent index exists at all is row 18, which
follows measurement in Stage 3 and gates neither this review nor cutover.

## 5. The local key envelope

Current `K_g` envelopes persist as bytes sealed under factor-protected `L_lock` (§13.3), scoped to the
principal/workspace custody entry. `L_local` is the legacy opener. The key store retains each generation
needed by SC-04's reference census; this is independent of the attribution floor.

**One envelope per (generation, purpose) is a logical row constraint, not an invocation counter.** The
former generation-only argument omitted abandoned attempts, retries and the sum across purposes. Current
v2 custody metadata records a durable `seal_reserved` count per custody root. Reserve before every
AES-GCM invocation under that root, including abandoned attempts and every purpose; rotate the custody
root or refuse before the 2^32nd reservation. Never reconstruct this count from surviving envelopes.
A resumable migration preserves the staged root's count; retrying cannot reset it. Fresh-root installation
and retained-envelope coverage obey SC-03/04. These metadata semantics do not change envelope bytes.

**`purpose` is bound, for row 2's reason.** Content-key and operational-credential seals preserve their
selected principal/workspace scope and distinct purpose. Without that field, otherwise identical
structures could be substituted. Mandatory factor custody includes receiving credentials (SC-08).

**Row 13 selects mandatory factor custody.** `L_lock` opens current envelopes; `L_local` is legacy
migration input only. Seal bytes/AAD remain independent of how the opening key was obtained, but a new
persistent store cannot choose promptless custody. SC-08 includes every future receiving credential and
forbids a persisted fallback opener. The seal vectors do not certify the complete profile inventory.

**Nonce accounting assumes unrewound, unbranched histories** (SC-09), for content keys and custody-key
seal budgets alike. Raw profile copies/restores duplicate keys and counters. Supported writable import
mints a fresh independent store id/key scope and reservation history; raw writable profile restoration
is outside the guarantee and cannot be assumed reliably detectable.

## 6. What it costs

**No bundle.** AES-GCM and HKDF are WebCrypto. The only bundle cost in the storage layer is row 2's 4.81 kB
for the synchronous primitive, already counted.

**Cold start absorbs per-record decryption, and this is the row where the record count enters.** §12 already
names cold start as the budget at risk for exactly this reason. The shape of the cost:

| Added to cold start         | Notes                                                                              |
| --------------------------- | ---------------------------------------------------------------------------------- |
| One key-store open + unseal | Once per workspace. Ahead of every content read, by §6.1's ordering                |
| One HKDF derive             | Once per generation held                                                           |
| One AES-GCM open per record | The variable term. Bounded by the trim, which collapses to a single `state` record |

**The trim is what keeps this flat**, and that is worth stating as a load-bearing property rather than a
maintenance detail: without it the store accumulates one record per update forever and cold start grows
without limit. With it, the steady state after a trim is one large decryption rather than thousands of small
ones.

**None of this is measured yet, and the baseline for measuring it now exists.** On the throttled profile,
with the store still plaintext, [performance.md](../performance.md) records cold start at 235.4 ms of a 2.5 s
budget and **content-root load at 54.3 ms of a 500 ms budget against 650 records**. The second is the row that
matters here: it scaled roughly linearly with the corpus during development — 166 records in 10.5 ms, 650 in
54.3 ms — which is the sensitivity that makes a per-record cost visible at all.

**The seam is already in place.** `src/lib/marks.ts` emits `done:boot`, `done:store-open`, `done:content-root`
and `done:store-ready`, and Stage 1 extends exactly those to bracket the key-store read, the unseal and
per-record decryption. That was built in Stage 0 so this row's regression would be **attributable** rather
than merely visible; Stage 1's exit criterion is where it gets checked.

## 7. What Stage 1 owes, and one thing it must not skip

**The old plaintext database has to be deleted, not orphaned.** Today the store is a single IndexedDB database
named `done` (`src/crdt/persistence.ts:17`) holding raw Yjs update bytes in an `updates` object store. Stage 1
gives stores per-_(principal, workspace)_ names, so the new code will simply never open `done` — and it will
sit there, full of plaintext content, on every existing installation. §11.1's no-plaintext-at-rest test
inspects **every** IndexedDB store, so this is a test failure rather than a subtlety; but it is the kind of
thing that gets found at the end of Stage 1 rather than planned into it. **Deleting it is a deliberate step
with a data-loss decision attached**, and it should be taken on the same terms row 2 took for `1:` journal
entries: the content is the author's own development data, Stage 2's cutover is a clean export → import
regardless, and shipping a plaintext reader to migrate it would defeat the point.

**Two smaller obligations.** The record store needs its own tests (§11.1), because the property fleet runs
with `persist: false` and will keep passing whatever the encrypted store does — [sequencing.md](../sequencing.md)
§3.2 already flags this as Stage 1's characteristic failure. And an unreadable record must be **left in place
and reported**, never dropped by the load path, inheriting row 2's rule for the journal; a load path that
discards what it cannot authenticate turns a key problem into data loss. SC-05 selects typed
repair-required refusal of normal open and whole-trim refusal, retaining all input carriers and needed
openers. SC-06 distinguishes fresh, resumable and damaged state; SC-07 includes the journal in clear.

**Not in this row.** The network envelope's wire format is row 4 and review 3b. The device-lock derivation is
row 13. Whether a persistent search index exists is row 18. The cutover's attribution carrier is row 21 and
[sequencing.md](../sequencing.md) §5.4 — still open, still gating Stage 2, and untouched by anything here.

## 8. The vectors

`node scripts/generate-record-vectors.mjs` writes them; `--check` fails if they are stale, and `pnpm check`
now runs it across all three vector files.

**The primitive KAT is not here, and its absence is structural.** AES-256-GCM's known-answer test lives in
[row 1's vectors](../../test/vectors/algorithm-suite.json), because row 1 selects the primitive and row 3
selects what is built out of it. What this file carries is **composition** — subkey derivation, the AAD
encoding, the framing — which is where a construction on a correct primitive still goes wrong, and which is
what review 3a most needs to see.

**Six record vectors and two envelope vectors.** An 18-byte keystroke update (the measured common case), a
`state` record, an empty update, a rotated generation under a different `K_g`, the same inputs under a second
workspace, and the same inputs under a second store of the same workspace — the last proving the store binding
by derivation, not only by AAD (`S0-3`). Then `K_g` sealed under `L_local` at two generations.

**Twenty negatives**, each one a field the load path trusts: wrong workspace by subkey and again by AAD, wrong
store by subkey (`wrong-store-subkey`, the derivation's falsifier — `P-3` falsifier 14), wrong principal, wrong
generation, `kind` swapped from update to state, `seq` renumbered, `v` downgraded, a flipped tag bit, a
truncated ciphertext, both cross-carrier confusions — a record opened with an envelope's AAD and an envelope
opened with a record's — and the AAD-only isolation group: one negative per bound field that changes that field
and nothing else, the record's label and store id and the envelope's six among them, so no field's binding
rides another's.

**The must-fail list cannot drift from what is actually asserted.** Row 2 established that a negative which
quietly stops failing is worse than no negative; a negative that is _published but never run_ is the same
defect one level up, and it is invisible without a comparison. The generator collects the labels it actually
asserted and fails if that set differs from the published list in either direction.

**Two things are inputs here that are not inputs in production**, and the file says so in its own text so a
reader who arrives at the JSON without this document cannot confuse them: nonces are fixed, because a vector
has to fix one to be a vector; and `L_local` is raw bytes, because a vector needs bytes, where legacy production
holds a non-extractable `CryptoKey` with no extractable representation at all.
