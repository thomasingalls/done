# Selection — TRD §15 row 2: the synchronous journal AEAD and its nonce discipline

**Lifetime/failure correction 2026-09-08:** [SC-01–07](../storage-contract.md) governs admission,
shared writer lifetime, generation-tagged journal references, repair-required open and journal-inclusive
clear. The seal format is unchanged. A generation fence in IndexedDB does not fence localStorage.

**Status:** selected, and folded into the TRD; measured on hardware on 2026-08-19, which found the budget
**exceeded at a 4 kB payload** — **and closed the same day by a compiled WASM seal** (§7). **Date:** 2026-08-18

## The selection

```
Primitive     XChaCha20-Poly1305 (draft-irtf-cfrg-xchacha-03)
Implementation wasm/journal-seal — audited RustCrypto chacha20poly1305,
              compiled no_std, base64-inlined, instantiated synchronously.
              (@noble/ciphers was selected first and lost on measurement: §7.)
Nonce         24 bytes from crypto.getRandomValues(), fresh per record.
              No counter. No durable state. Nothing to lose in a crash.
Subkey        K_journal = HKDF-SHA256(ikm = K_g, salt = "",
                                      info = LP("done/journal/v1") || LP(workspace_id),
                                      L = 32)
              Derived once at open via WebCrypto deriveBits — async, so free.
AAD           LP("done/jrnl/v1") || LP(workspace_id) || LP(decimal gen) || LP(journal_storage_key)
Record        "2:" || base64( u32be(gen) || nonce[24] || ciphertext || tag[16] )

              LP(s) = uint16be(byteLength(utf8 s)) || utf8 s
```

Everything below is why, and what it cost.

---

## 1. Why this path needs a JS AEAD at all

The constraint chain is short and each link is already in the TRD, but it is worth walking because the
conclusion looks like a dependency being added for convenience and is not.

The journal is a write-ahead log written **synchronously**, inside a handler that must not return until the
write has happened (TRD §6.1). It exists to close the window where the browser can terminate the page between
a Yjs transaction and IndexedDB's asynchronous commit. It now holds content, so it must be encrypted — and
`crypto.subtle.encrypt` returns a promise, so WebCrypto cannot be used inside that handler. TRD §6.1 records
the decision to preserve the crash-safety contract rather than redesign it, which leaves exactly one option:
a synchronous AEAD in JS or WASM.

**One WebCrypto primitive does survive the synchronous constraint, and the design leans on it.**
`crypto.getRandomValues()` is synchronous — unlike everything under `crypto.subtle`. That is what makes a
random-nonce discipline available on this path at all, and it is load-bearing rather than incidental.

---

## 2. The nonce discipline, which is the actual question

Row 2's constraint is one sentence: _must survive a page kill without durable counter state_. TRD §6.1 spells
out why this is sharper than it sounds — a counter-based nonce whose last value was not durably recorded can
repeat after exactly the crash the journal exists to survive, and for most AEADs nonce reuse is catastrophic
rather than degrading. The failure is also **retroactive**: ciphertext already written stays broken, which is
why §5.2 of the sequencing plan puts this construction in front of a reviewer before the cutover writes any
data that matters.

**Selected: 24 random bytes per record, from `crypto.getRandomValues()`.**

The argument is that a random nonce has no state, so there is nothing for a crash to lose. What makes it
_safe_ is the width. For q records the collision probability is about q²/2^193; at q = 2^64 — absurdly beyond
any journal, which is cleared every 250 ms — that is around 2^-65.

**The property worth insisting on is not the number, it is that the number is unconditional.** A 192-bit
random nonce is safe without reference to how many journal entries this app will ever write. A 96-bit nonce
would also be fine _at the volumes this journal actually sees_, and that is the problem: the safety argument
would then be a claim about application behaviour, which a reviewer has to verify and a later change can
silently invalidate. Nonce-reuse faults are retroactive and silent, so the assumption that rots is the worst
possible place to be carrying the guarantee.

That is the whole reason to take XChaCha20-Poly1305 over RFC 8439 ChaCha20-Poly1305. It is not that the
extended nonce is faster or better studied; it is that it moves the safety argument off the application and
into the primitive.

### Rejected — a fresh subkey per page session, with a counter

TRD §6.1 names this as the alternative escape route: _derive a fresh journal subkey per page session so a
repeated counter lands under a different key_. It works, and it would permit a 96-bit primitive. **It is
declined**, for three reasons in ascending order of importance:

1. It does not remove the randomness argument, it relocates it. Session salts must not collide either, so the
   birthday bound reappears one level down, now behind more machinery.
2. It puts a session registry on the replay path. Replay would have to find every session id present in the
   journal and re-derive a subkey for each. That path is the crash path — the one component whose failure mode
   is silent data loss — and adding state to it to save nonce bits is the wrong trade.
3. It creates a way to lose data that random nonces do not have: if the session id is not written before the
   first record under it, or is cleared independently of the records it covers, those records become
   permanently unreadable. The journal's entire job is to still be readable after an abrupt kill.

### Rejected — reusing AES-256-GCM from the store and envelope paths

Forbidden by TRD §13.2: _one primitive key must not be reused across the asynchronous and synchronous
constructions_, and TRD §13.10 states the criterion as no primitive shared between the two paths. Beyond the
rule, AES-GCM's 96-bit nonce puts us back in the conditional-safety argument above, and its misuse penalty is
the harshest of the candidates. The constraint is doing real work here rather than being satisfied
incidentally.

## 3. Key derivation, and why WebCrypto still does it

`K_journal` is derived **once at open**, not per write. The synchronous constraint binds the per-record path
only, so derivation can use WebCrypto's HKDF and does — which keeps a JS HKDF out of the bundle entirely.

`deriveBits` rather than `deriveKey`, because the AEAD needs raw bytes. TRD §6.1 already sanctions this as
_the narrow exception to non-extractable runtime keys, forced by the synchronous contract_: the subkey lives
in slot memory as bytes, is cleared at sign-out or lock, and is re-derived at unlock. It must never be `K_g`
itself, a device private credential, or recovery material.

**The generation is deliberately absent from `info`.** `K_g` is already the content key _for one generation_,
so any subkey derived from it is generation-specific by construction; adding `gen` to the derivation would be
redundant. What the record's cleartext `gen` field does is select **which `K_g` to derive from** during
replay — which is a different job, and the reason that field has to exist at all.

---

## 4. The associated data, and two details that are easy to get wrong

**Length-prefixed fields, not delimiter-joined.** `LP(s) = uint16be(len) || utf8(s)`. A delimiter-joined AAD
is not injective: a workspace id containing the delimiter shifts every field after it, and two different
contexts can encode to identical bytes — which is precisely the binding AAD exists to provide. Length
prefixes make the encoding injective, which is the only property it actually needs.

**`gen` is a cleartext header field, so it is in the AAD.** The record has to carry its generation in the
clear or replay cannot pick a key. Any cleartext field a reader trusts must be authenticated, or it can be
edited by whoever can write localStorage.

**`journal_storage_key` is in the AAD** so an entry cannot be copied into another slot. Yjs updates are
order-independent and idempotent, so moving one is _probably_ harmless — but "probably harmless" is not a
property worth relying on when binding it costs nothing.

**`workspace_id` appears in both the derivation and the AAD.** This is deliberate redundancy: the subkey is
already workspace-bound, so the AAD copy adds no cryptographic strength. It makes the record self-describing,
which is worth the four bytes.

## 5. What it costs, measured

Numbers taken on 2026-08-18. The bundle figures are real builds; the latency figures are **not yet the
budget's measurement** — see §7.

| Cost                                                 | Measured    | Against                                           |
| ---------------------------------------------------- | ----------- | ------------------------------------------------- |
| Bundle, AEAD alone, tree-shaken + minified + gzipped | **4.81 kB** | 43.7 kB of headroom (306.3 kB of a 350 kB budget) |
| Bundle, if a JS HKDF were also needed                | 7.44 kB     | Avoided — WebCrypto derives at open               |
| Runtime dependencies added                           | **none**    | `@noble/ciphers` has no `dependencies`            |
| Seal, 18-byte update, p95                            | **7.8 µs**  | < 1 ms p95 budget (TRD §12)                       |
| Seal, 419-byte update, p95                           | 14.3 µs     | "                                                 |
| Seal, 4 kB update, p95                               | 31.9 µs     | "                                                 |

**Payload sizes are measured, not assumed.** One keystroke in a `Y.Text` produces a 15–18 byte Yjs update
(n=78, mean 18); a 400-character paste produces 419 bytes. So the common case for this path is an 18-byte
plaintext.

**Which means the overhead exceeds the payload, and that is fine.** A sealed keystroke entry is 80 base64
characters against 24 today — 4 bytes of `gen`, 24 of nonce and 16 of tag on top of 18 bytes of content,
then base64. At 4 kB the expansion is under 1%. The journal holds only what has not yet flushed through a
250 ms window, so a few hundred entries is its realistic ceiling and localStorage quota is not threatened.
It is still worth stating, because a 3.3× expansion on the common case is the sort of thing that is
discovered later and mistaken for a defect.

## 6. The implementation, and the one thing to tell the reviewer

`@noble/ciphers` — MIT, no runtime dependencies, tree-shakes to the single `xchacha20poly1305` export, tested
against Wycheproof and cross-library vectors, and fuzzed in a separate repo.

**Its audit history does not cover the version we would ship, and review 3a should hear that from us rather
than find it.** Per the package's own README: independently audited by Cure53 in September 2024 **at version
1.0.0** (scope: everything, funded by OpenSats), and self-audited in April 2026 **at version 2.2.0**. The
current release is 2.3.0. So the independent audit is two majors behind, and the honest statement is that we
are selecting a library with a real independent audit in its history and a diff since.

Three ways to answer that, for the reviewer to weigh:

- **Ship 2.3.0 and pin it**, with the diff-since-audit noted. Cheapest, and the exposure is one narrow export.
- **Pin to the last independently audited line.** Buys the audit exactly, costs the fixes since.
- **Verify against Wycheproof in our own suite**, which is cheap and worth doing whichever version is chosen.

The alternative implementations were considered and lose on bundle rather than on merit: `libsodium-wrappers`
is the reference implementation but ships a WASM/asm.js blob far past the 43.7 kB of headroom, and a
hand-rolled WASM build adds a toolchain to the crash path for a primitive already small in JS.

> **That last clause was wrong, and measurement is what showed it.** It bundles two objections — a toolchain on
> the crash path, and a primitive not worth the trouble — and the second is false: the pure-JS primitive misses
> the budget by twice at 4 kB, so it was never "small enough" in the sense that mattered. The first survives as a
> real cost and is now §13.10's open criterion question rather than a reason not to build. **A compiled module is
> also not "hand-rolled"** — the source is the audited crate; what the second toolchain changes is the artifact,
> not the implementation. See §7.

**The primitive is the load-bearing choice; the implementation is swappable**, and it has since been swapped.
The construction, the vectors and this document survived the change unchanged, which is what that claim
predicted.

## 7. What is still open, and what Stage 1 owes

**The budget's own measurement has not been taken, and one of the two reasons has changed.** TRD §12's
`< 1 ms p95` is specified _on a low-end device_. A browser benchmark now exists — `test/latency/journal.spec.ts`,
recorded in [performance.md](../performance.md) — and it closes both gaps this section named against §5's
figures: it runs in Chrome rather than Node, and it uses `lib0/buffer` for base64 as the journal does. **The
seal itself came out at 7.6 µs against §5's 7.8 µs, so neither gap mattered for the primitive**; they matter
one level up, where base64 turns out to cost about as much as the cipher at 4 kB.

**What the browser run cannot supply is the statistic the budget names.** §12 is a p95 of one write, and CPU
throttling under CDP stalls the thread rather than modelling a slower core, so its stalls land inside
individually-timed operations and become the tail — the plaintext level shows the same inflation while
performing no cryptography at all, which is the proof rather than the suspicion. So the throttled profile
yields a trustworthy mean and no trustworthy tail.

**The measurement has now been taken on hardware, and this row's margin argument did not survive it.** A
Pixel 9a gives **145 µs p95 at the common case and 1 930 µs at 4 kB**, against 1 ms. So the budget holds where
the journal actually sits and is exceeded by about twice on a large paste. It reproduces within 1.4% across two
runs and survives a drift check.

**It was carried as a Stage 1 defect for about six hours, and then fixed.** `wasm/journal-seal` compiles the
audited RustCrypto `chacha20poly1305` crate to a 6 465-byte `no_std` module — no allocator, no wasm-bindgen,
base64-inlined, instantiated synchronously — and on the same handset the full write becomes **35 µs, 65 µs and
240 µs p95**, the last with 4.2× of margin. **The implementation swap is invisible to everything else in this
document**: same primitive, same nonce discipline, same record format, same published vectors, which the module
reproduces byte for byte on every `pnpm check`.

**Three things the fix turned up that the selection had assumed.** The module is **4.5 kB gzipped through the
bundler, 0.7 kB _less_ than `@noble/ciphers`** — so §6's bundle argument against WASM was not merely beatable, it
had the sign backwards for a purpose-built module. It is **faster than libsodium** (45.3 µs against 51.8 at
4 kB), which was measured as the ceiling of what any WASM cipher could buy. And `opt-level = "z"` — the obvious
setting for a module chosen partly on size — reaches only 1.17× over `@noble`, so **the size-first default would
have produced a module that fitted and did not fix anything.**

**The way this row was wrong is worth more than the number.** §5 reasoned from a 128× desktop margin and the
observation that "a phone is typically 5–20× slower on JS microbenchmarks, not 128×". **That form of argument is
unsound, not merely optimistic.** Against desktop this phone runs the cipher 12×, 19× and 43× slower as the
payload grows, while base64 and the storage write run only 1.3×, 2.3× and 5.3× slower — pure-JS arithmetic
degrades and paths reaching native code do not. There is no single scalar to be careful with, so no more careful
version of the extrapolation would have reached the right answer.

**The oversize question is answered, and not by this row's module** (`S0-3`, `P-3`,
`f-9b49b74-journal-seal-64k-gap`). The seal refuses above 65,536 bytes by throwing — **after** the Yjs
transaction that produced the update — so the document holds a change nothing durable records, and §5's
measurements stop at 4 kB with the boundary left to Stage 1.

**The buffer was never the binding constraint.** TRD §12's budget is exhausted at about **20 kB** on the
handset this row measured, so an update reaching 64 KiB has already breached a budget §12 calls a correctness
property. Enlarging the buffer moves a wall that is in the wrong place; **chunking does not help either**,
because a segmented WAL seals the same bytes on the same thread inside the same handler. So the repair is
TRD §6.1's: **no operation may produce an update above `MAX_UPDATE`**, with an admission check in front of the
seal as the backstop. **This module does not change**, and its guard becomes a boundary admission makes
unreachable.

**And the journal's contract narrowed to locally originated updates.** A remote update is protected by §6.1's
content-batch-before-heads ordering, which re-delivers it after a crash — a stronger guarantee than this
journal offers, and the only case whose size this device does not control.

**A judgment call Stage 1 has to take, flagged here rather than discovered there:** what happens to `1:`
entries — plaintext journal records written by the current build — when the encrypted journal first opens.
The recommendation is **refuse and report, do not replay**. A `1:` entry is by definition plaintext content
at rest, which TRD §6.1's _must not happen_ list forbids and TRD §11.1's no-plaintext-at-rest test would
catch; replaying it means shipping a plaintext reader. The cost is bounded at whatever had not flushed in a
250 ms window on one upgrade, and Stage 2's cutover is a clean export→import into a fresh store regardless.
It is a data-loss decision, however small, so it should be taken rather than defaulted.

**A rule carried forward from the existing code.** `readJournal` today leaves an unreadable entry intact
because _silent deletion is the wrong failure mode for a WAL_. That must survive encryption: an entry failing
authentication is left in place and reported, never dropped by the replay path. It does mean a corrupt or
foreign entry never clears itself, so removal needs to be an explicit repair action — a small open detail,
noted so it is not solved accidentally by making replay delete things.

**Not in this row.** The content-store record format is row 3 and the algorithm suite is row 1; both are
review 3a scope but neither is settled here. Rows 13 and the storage-facing part of 14 are also 3a's scope
and are not started ([progress.md](../progress.md)).

## 8. The vectors

`node scripts/generate-journal-vectors.mjs` writes them; `--check` fails if they are stale. The generator
verifies itself on every run: every composition vector must round-trip, and every negative must fail to
authenticate. A "must fail" list whose entries quietly succeed is worse than no list.

**Two kinds, and the distinction is the point.**

The **primitive KAT** is copied from draft-irtf-cfrg-xchacha-03 §A.3.1 and must never be regenerated — a
known-answer test produced by the code it checks proves only that the code agrees with itself. It confirms
the implementation is XChaCha20-Poly1305 and nothing else. `@noble/ciphers` 2.3.0 reproduces it exactly.

The **composition vectors** are ours, and they are the ones review 3a actually needs: they pin subkey
derivation, the AAD encoding and the record framing, which is where a construction built on a correct
primitive still goes wrong. Four cases — empty update, an 18-byte keystroke update, a rotated generation, and
the same inputs under a second workspace — plus six negatives: wrong workspace, wrong generation, moved slot,
flipped tag bit, truncated record, and a `1:` version prefix.

**Nonces are inputs in the vectors.** They have to be fixed for a vector to be a vector. That fixing is not
the nonce discipline, and the file says so in its own text so the two cannot be confused by a reader who
arrives at the JSON without this document.
