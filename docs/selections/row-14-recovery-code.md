## The selection

```
The code

  Entropy       125 bits. Generated, never chosen by a human, never truncated.
  Alphabet      Crockford Base32 — 0123456789ABCDEFGHJKMNPQRSTVWXYZ
                I, L, O and U are absent.
  Generation    25 bytes from crypto.getRandomValues();
                symbol i = ALPHABET[byte_i & 0x1f].
                256 = 8 x 32, so the mask is uniform. No rejection sampling,
                no modulo bias, no bit packing.
  Display       AZC52-QK9FE-HC6M7-VS01J-DA3NY
                Five groups of five, uppercase.
  Normalization Drop hyphens and whitespace, uppercase, then O -> 0, I -> 1, L -> 1.
                U is rejected, not folded. Exactly 25 symbols.
  Stretching    None. No Argon2id, no PBKDF2.

The envelope  (service-held, opaque)

  RecoveryEnvelope = { v: 1, salt: Uint8Array(16),
                       nonce: Uint8Array(12), ct: Uint8Array }
                     // plaintext = raw X25519 R_priv[32] || binary RootCommitment[32]
                     //             || raw Ed25519 bootstrap seed[32]
                     // ct is exactly 112 bytes: plaintext[96] plus GCM tag[16]

  K_rec = HKDF-SHA256(ikm = utf8(canonical code), salt = salt,
                      info = LP("done/recovery/v1") || LP(principal_id), L = 32)

  AAD   = LP("done/recovery/v1") || LP(principal_id) || LP(dec v) || LP(hex R_pub)

  Seal  AES-256-GCM. The salt is fresh per seal, so K_rec is fresh per seal and
        exactly one message is encrypted under it, conditioned on nonrepeating
        randomness across seals, including restores/clones.

Replacement  (PRD §7.6; the protocol half is review 3b's)

  Gate 1  Content access, proven by use — the flow unwraps the current
          generation before it may create a new keypair.
  Gate 2  A single-use service challenge, bound to the operation:
          SHA-256( LP("done/recovery-replace/v1") || LP(dec v)
                   || LP(hex intent_id) || LP(hex nonce) )
          answered by an assertion from the account credential (row 12).
          nonce  32 fresh bytes per attempt, service-issued, retired on use.
          intent_id  row 15's replace-recovery transition id, which already
                     binds kind, lineage, parent epoch and the new R_pub.
          Not bound: principal or credential id. This challenge is
                     service-issued and names the operation as the service
                     knows it, where §13.9's is client-constructed for a
                     device-local gate and names device-local things.
  Gate 3  The device lock, where the slot uses one — implied by gate 1.
  Not required: the old code.

  The payload  row 15's replace-recovery parts, and every value is EXACT
               bytes: counter, new R_pub, the sealed envelope including its
               tag, the root commitment, and the wrap for every rewrapped
               generation. Not a list of generation numbers -- a digest over
               WHICH generations were rewrapped, and not over what they were
               rewrapped TO, cannot make "exactly the old or exactly the new"
               mean one exact complete set won.

  Exposure     the payload carries successor-generation. Resealing leaves K_g
               unchanged, so an exposed R_priv still opens current content
               after a replacement that only re-encrypts it. Since this flow
               exists for the user who has lost -- OR EXPOSED -- the code, it
               rotates forward. The only way not to is the explicit value
               'none-lost-not-copied', available solely where the product can
               distinguish lost from copied and says so to the user.

                LP(s) = uint16be(byteLength(utf8 s)) || utf8 s
```

## 1. The row's question is already half-answered, and by the PRD

TRD §15 states row 14's constraint as _decides whether stretching is needed at all_, and §13.10 offers
"Argon2id, or none" with the note that **a generated high-entropy code needs little stretching; a typed one
does.** Read as a menu, that is a choice between two KDFs. It is not.

The deciding constraint is one sentence PRD §7.6 has already written, in the course of rejecting something
else. Passwords are refused as recovery factors **because server-held sealed data permits offline guessing**.
That sentence describes our envelope exactly: the sealed `R_priv` lives at the service, it is fetched by a
replacement device, and from the moment it is fetched every guess is offline and unrateable. **So the threat
model was fixed before this row was opened, and what remains is a number.**

That reframes the work. Stretching is the technique for making a _deficit_ of entropy expensive to exploit. It
converts entropy you do not have into time you hope the attacker will not spend. The question is therefore not
"which KDF" but **"is there a deficit", and the answer is ours to decide, because we generate the code.**

**Selected: no deficit, and therefore no stretching.** 125 bits, and HKDF only.

---

## 2. Why 125 bits, and why the argument has the shape it does

At 125 bits an exhaustive search is 4.25 × 10³⁷ candidates. Against an adversary running 10¹² guesses per
second — an ASIC budget, not a laptop — that is **1.3 × 10¹⁸ years**. Grant them a thousandfold more and it is
10¹⁵ years. The margin is not close enough to argue about, which is the property being bought.

**What a work factor would add is a multiplier on a number that is already unreachable, and a condition on an
argument that currently has none.** Argon2id at 100 ms a guess is a factor of 10⁸ or so on top of 10¹⁸ years.
Nothing in the product is safer afterwards. What changes is the _form_ of the safety claim: it stops being
"the search space is too large" and becomes "the search space is large and each guess is expensive", and the
second half of that decays with hardware, needs parameters, needs those parameters revisited, and needs a
reviewer to check them. **This is row 2's argument again, in a different place.** There, a 96-bit nonce would
have been fine at this journal's volumes and was refused because the safety claim would have become a claim
about application behaviour. Here a 60-bit code plus Argon2id would probably be fine too, and is refused for
the same reason: a guarantee that rests on an assumption is a guarantee that can quietly stop being true.

**The cost of taking it this way is zero, which is what makes it easy.** HKDF-SHA-256 and AES-256-GCM are
already row 1's selections and already in WebCrypto; the encoder and the normalizer are a few dozen lines of
arithmetic. Argon2id has no WebCrypto implementation, so it would arrive as a WASM dependency on the
account-creation path against the 43.7 kB of bundle headroom [performance.md](../performance.md) records.
PBKDF2 _is_ in WebCrypto and would be free, and is refused on the same grounds as Argon2id plus one more: it
is the memory-cheap option, so choosing it to feel careful buys the least real work per unit of user-visible
delay of anything on the menu.

**Why 125 and not 128.** The layout is the binding constraint, not the number. Five groups of five is the
most transcribable arrangement available and 25 symbols is what it holds; 128 bits needs 26, which groups into
nothing. **The distinction between 2¹²⁵ and 2¹²⁸ is not reachable by any adversary that exists**, and the
project's own convention is to prefer the arrangement a person can copy correctly. Said plainly so nobody has
to reconstruct it: the three bits were spent on the hyphens.

**One invariant carries the whole argument, and it should be written into the TRD rather than left implied:
the code is generated by the app at full width and is never user-chosen, never user-extended, and never
displayed or accepted in a truncated form.** If any of those ever changes, the stretching question reopens
that day, and it reopens as a real one.

## 3. The alphabet and the generation

**Crockford Base32.** The four absent characters are the selection: `I`, `L` and `O` because they are what a
human confuses with `1`, `1` and `0`, and `U` because Crockford removes it so a generated code does not spell
something its owner has to read aloud to a support person. What that buys is not aesthetic — it means the
input field can **map** `O` to `0` and `I`/`L` to `1` without ambiguity, because the generator can never have
emitted the letters. A correct transcription of a badly-rendered code still opens the workspace.

That mapping only works because the letters are absent from the alphabet. If they were present, normalization
would collide two distinct codes onto one, and the vectors assert their absence rather than trusting it.

**`byte & 0x1f`, and why the three discarded bits are deliberate.** 256 = 8 × 32, so masking the low five bits
of a random byte draws each symbol with probability exactly 1/32 — uniform, no rejection loop, no modulo bias.
The generator asserts this structurally, by counting preimages: **every symbol must have exactly eight of the
256 byte values, or the 125-bit claim is false.** That check exists because this is where entropy is lost
silently. A `% 33` or a 36-character alphabet would still produce codes that look right, still seal, still
open, and would be weaker than the document claims with nothing to show for it.

The obvious alternative — pack 125 bits out of 16 bytes rather than spend 25 — saves nine bytes of a value
that is never stored anywhere, and adds a bit-shuffling step whose failure mode is a code with less entropy
than advertised. It is declined for that trade alone.

**The IKM is the 25 ASCII characters, not the bits packed down.** HKDF's security rests on the entropy in its
input, not the input's density, so the packing step would buy nothing and is exactly the step above.

## 4. The envelope, and what is bound

**`principal_id`, not an account identifier — and the reason is a lifecycle one.** PRD §6.2 is explicit that
account creation binds an account onto the _existing_ principal rather than minting a replacement identity:
"the existing principal, device identity, home-workspace membership and content root carry over". So the
principal is the identifier that is stable across the very event that creates this keypair. Binding it also
keeps this row consistent with row 3, which binds `principal_id` in every content record for the ordinary
two-principals-on-one-profile case (PRD §6.7), and avoids inventing a term TRD §0 does not have.

**`R_pub` is in the AAD, and it is the least obvious of the four fields.** PRD §7.6 makes replacement an
_atomic_ replace of the public key, the wraps and the sealed envelope. Binding the public key means a
mismatched set fails at the unseal, immediately and with an unambiguous cause, rather than a few steps later
when the content-key wraps do not open. It costs nothing and turns a confusing failure into a clear one.
The negative vector `rebound-public-key` is that case.

**`v` is in the AAD** for row 1's reason: the carrier version selects the whole suite, so it has to be
authenticated or a renumbered envelope becomes a way to select a different one.

**The GCM nonce question does not arise here, and that is worth stating rather than leaving to inference.**
A fresh 16-byte salt per seal means a fresh `K_rec` per seal, and exactly one message is ever encrypted under
it. Nonce reuse is not avoided by discipline; it is **structurally unreachable**. The 12 random bytes are
there so that an implementation which someday reuses a salt does not immediately catastrophize — belt and
braces on a construction that does not need either.

The salt is also what makes any multi-target precomputation question unaskable. At 125 bits it was not
askable anyway; the sixteen bytes are cheap enough not to reason about.

**Must not happen.** The code is never transmitted to the service, never persisted by the client, and — once
the account exists — never re-displayed. `K_rec` exists for the duration of one seal or one unseal.

## 5. Step-up: what "fresh account authentication" is

PRD §7.6 requires replacement to run "from a device that already has content access: after fresh account
authentication and an explicit confirmation", and leaves the mechanism to the TRD. Three gates, and the
useful observation is that **two of them are free.**

**Gate 1 — content access, proven by use rather than by a flag.** Replacement must rewrap every required
content-key generation to the new `R_pub`, so it already has to open them. Checking a permission and then
doing the work is two things that can disagree; requiring the work _is_ the check.

**Gate 3 — the device lock, where the slot has one.** TRD §13.3 makes the lock the gate on opening `K_g`
envelopes, and gate 1 opens them. So this is implied, not a second prompt, and an implementation that adds one
has misread where the lock sits.

**Gate 2 is the only one that needs designing, and it is a challenge rather than a timer.** The natural
instinct is a freshness window — re-authenticate if the last assertion is older than five minutes. That is a
parameter with no principled value, and the thing it approximates is "this assertion was collected for _this
operation_". So bind it directly:

```
challenge = SHA-256( LP("done/recovery-replace/v1") || LP(dec v)
                     || LP(hex intent_id) || LP(hex nonce) )

answered by  an assertion from the account credential (row 12) over that
             challenge -- same relying party, same credential, same ceremony
nonce        32 fresh bytes per attempt, issued by the service, retired on use
```

An assertion collected for an ordinary sign-in cannot be presented for a replacement, and one collected for a
replacement cannot be redirected to a different one. No clock, nothing to tune, nothing to get wrong on a
device whose clock is off.

**Three things about that construction were not in this section's first draft, and each is worth its
paragraph.**

**The nonce is what makes _single-use_ true rather than said.** The draft described a "single-use service
challenge" whose fields were the label, the principal and a hash of the new public key — all of which are
functions of the operation. A challenge that is a pure function of the operation is the same challenge every
time it is asked for, so there is nothing the service can retire and nothing an assertion is fresh
_relative to_. An assertion collected for a replacement that never completed would stay presentable
indefinitely. **This is [row 9](./row-9-chain-head-discovery.md)'s finding at a different message**: without a
nonce a signed artifact is a standing artifact, any intermediary can re-serve it forever, and replay needs no
key at all. §13.9's slot-unlock challenge — written _later_, citing this section as its source — carries
`LP(hex nonce)` and 32 fresh bytes per attempt, so the omission here was visible from the other end of the
design before it was visible from this one.

**It binds the transition id rather than the new public key, and [row 15](./row-15-transitions.md) is why.**
When this section was drafted the operation had no name, so it named the operation's _target_ instead. Row 15
gave it one: a `replace-recovery` intent whose id is `SHA-256(Intent)` over `kind`, the workspace, the lineage,
the parent epoch, the target and the payload digest — and the new public key is inside that payload. So
binding the key beside the id would be **a second binding of a fact already inside it**, which rows 10, 12 and
15 each refused for the same reason. What the change buys beyond tidiness: `kind` is inside the id, so **a
step-up assertion minted for a `replace-recovery` cannot be redirected to a `retire`** — PRD §6.10's _a
deliberate downgrade must not silently become account deletion_, one level further out than row 15 took it.

**It binds no principal and no credential id, where §13.9's slot-unlock challenge binds both.** That looks like
an inconsistency and is a difference in provenance. The slot-unlock challenge is **client-constructed for a
device-local gate**, so it names device-local things — a principal in this profile, a credential in this slot.
This one is **service-issued for a service operation**, so it names the operation as the service knows it: an
intent it holds and a nonce it minted. A service-issued challenge naming a device-local identifier would be
taking the client's word for it, which is the shape row 12 spent its length removing. And binding a credential
id would forbid answering from a second passkey the account has registered — a feature rather than an attack,
since every credential the account holds is equally authoritative for it.

**The old code is deliberately not required, and the reason is that requiring it would defeat the feature.**
Replacement exists for the user who still holds their devices and has lost — or exposed — the code. Demanding
the lost object is the one requirement guaranteed to be unmeetable exactly when the flow is needed.

**The residual, named rather than left for the reviewer to find.** Because the old code is not required,
someone holding a device _and_ the account credential can replace the recovery envelope and thereby destroy
the legitimate owner's recovery path. That party already has content access, so this widens no confidentiality
boundary — it is an availability loss, and it is strictly less than what the same party can already do by
deleting the account. It is accepted on those terms, and the explicit confirmation PRD §7.6 requires is where
it is surfaced.

**This section is review 3b's, and is written here because §2 cannot be judged without it.** Whether the code
needs stretching depends on whether the envelope is offline-attackable, which depends on how the service
serves it.

**Of the two things it originally handed to 3b, one is closed and one is deliberately still a question.** The
atomic-replace semantics at the service boundary are row 15's `kind: 'replace-recovery'`, and an interruption
now leaves exactly the old envelope or exactly the new. What remains is **whether the service rate-limits
envelope fetch** — it should, and it changes nothing about the entropy, because the attacker who matters has
already fetched. That is a service-hardening question rather than a construction, and it is **put to the
reviewer as a question rather than left in the register as an open row**; §13.11 gates on the second and not
on the first.

## 6. Confirmation UX, and the distinction that gets implemented wrong

PRD §7.6 fixes the policy: generated, explained, stored off this device, **re-entered before the account
exists**, never re-displayed afterwards, replaceable but not recoverable. What this row adds is the mechanism.

**Re-entry is full, and paste is allowed.** PRD §7.6 already refuses to claim more than re-entry can prove —
"a user who pastes the code into a note on the same phone passes every test the app can run" — and blocking
paste would not change that. What it _would_ do is break password managers, which are the realistic good home
for this code and the one place an ordinary person's copy survives a lost phone. **The app should not run a
ceremony whose only effect is to obstruct the storage it wants the user to choose.** A partial check — confirm
symbols 3, 11 and 19 — is declined for a related reason: it proves less, and 25 characters is short enough
that full re-entry is not the hardship the pattern exists to relieve.

**The one distinction to get right: "never re-displayed" starts when the account exists.** Before that moment
there is no account, the code is in memory, nothing has been sealed to it, and letting the user see it again
is free. After it, re-display would require retaining a recoverable copy — the exact thing the design refuses.
These are two different states of the same screen and the natural implementation gets it wrong by making one
component serve both. **A "show it again" control must not survive account creation.**

**Abandonment discards.** If the user leaves before re-entry completes, the account does not exist and the
code is dropped; resuming generates a **new** one. A code that survives an abandoned attempt is a secret with
an unclear lifetime sitting in memory or, worse, in storage.

**No rate limit at re-entry, and none that matters at recovery.** At creation the code is in memory and a
limiter would only lock a user out of their own unfinished signup. At recovery the envelope has been fetched
and every attempt is local; a client-side counter is decoration. **That is not a weakness to apologize for —
it is the reason the entropy is 125 bits.** The construction is honest about which component carries the
guarantee.

**Normalization runs live in the field**, so a user who wrote `O` for `0` sees their input become the code
rather than being told they are wrong. `U` gets its own message — _that character never appears in a code_ —
because it is the one input where the app knows something specific about the mistake.

**What is said at the moment of generation is PRD §7.6's sentence, not a paraphrase:** not on this device, not
only in this browser, somewhere you would still have if this device were stolen tonight. The copy is question
12 in PRD §11 and stays there; this row supplies the constraints the copy has to sit inside, not the words.

## 8. What is still open, and what Stage 4 owes

**Both halves are now closed** — the storage half on 2026-08-18, §5's step-up on 2026-08-20 — and closing the
second closed review 3b's scope with it. TRD §15 no longer splits this row between the two reviews; row 20 is
the only row left appearing in both halves of the register.

**One dependency worth flagging early.** `R_priv` is an X25519 scalar because row 1 selected HPKE with
DHKEM(X25519). Row 1 also records that **Ed25519's browser availability is asserted rather than verified**, on
the same missing browser-support floor. X25519 in WebCrypto is the same class of assumption and is load-bearing
in the same stage. It is one question — _what does this project support?_ — and it should be answered once,
before Stage 4, rather than three times in three rows.

**A Stage 4 implementation note, recorded here so it is planned rather than discovered.** The unsealed
`R_priv` exists for one brief interval at account creation, during which the content generation is wrapped to
`R_pub` and the envelope is written; TRD §13.3 and PRD §6.2 both require it to be erased at the end of it. That
erasure is on an interruptible path — the same crash-safety shape TRD §6.5 gives to destructive clears — and
an interrupted creation must resolve to _no account_ rather than to an account whose recovery envelope was
never written.

**A terminology collision, found while writing this and since fixed.** `recovery` already meant something
in this codebase, and it was not this: the **membership repair** surface — cards retained because their
collection membership can no longer be shown. A third sense had appeared too, the synchronous log that
`persistence.ts` called a "recovery journal" while row 2 called it the crash journal. Stage 4 was about to
add `R_priv`, the recovery code and the recovery envelope to that, so the card sense is now **unfiled** and
the log is the **crash journal**. The rename reached the export archive — `recovery.md` became `unfiled.md`
— which §2.1's argument makes free today and a format change after Stage 2. Recorded in
[decisions.md](../decisions.md).

**Not in this row.** The device lock's own derivation and enrollment migration are row 13. It touches §13.3's
PRF-or-code framing, which is adjacent to this row's presentation question, and the two should be read
together by the reviewer.

**One question is put to 3b rather than answered here**, and it is the only such item in either scope:
whether the service rate-limits envelope fetch (§5). It is service hardening rather than a construction, it
changes nothing about the entropy in §2, and it has no vector because there is nothing yet to measure it
against.

## 9. The vectors

`node scripts/generate-recovery-vectors.mjs` writes them; `--check` fails if they are stale, and
`pnpm vectors:check` runs it inside `pnpm check`. The generator verifies itself on every run.

**No primitive KATs here, on purpose.** HKDF-SHA-256 and AES-256-GCM are row 1's selections and row 1's
vectors carry their published known-answer tests (RFC 5869, GCM Test Case 16). Repeating them would create a
second place for the same fact to be true.

**One published KAT is added, because this row introduces a keypair.** The recovery keypair in the vectors is
RFC 7748 §6.1's — and the generator **derives the public key from the private scalar and refuses to write the
file unless they match.** An AAD that binds a public key to a private one proves nothing if the vector's own
two halves are unrelated blobs.

**Four kinds of vector.** _Encoding_ — four cases pinning the alphabet, the mask and the grouping, including
one whose input bytes have their high bits set and must encode identically to a case that does not, which is
what catches a modulo where a mask belongs. _Normalization_ — eight cases, every confusable in both
directions, wrong separators, no separators, and one case where every rule fires on the same input, which is
where an implementation that applies them in the wrong order fails. _Rejections_ — four inputs that must be
refused, including `U` and both length errors. _Seal_ — two envelopes differing only in principal.

**Nine negatives on the envelope**: wrong code, wrong salt, wrong principal, an envelope re-paired with a
public key that is not its own, a downgraded version, a flipped tag bit, a truncated ciphertext, and the two
`aad-only-` isolations that separate the AAD's binding from the derivation's.

**And five on the step-up, which are the ones with a shape worth reading.** One worked assertion — fully
pinned, since Ed25519 is deterministic — then `stepup-other-passkey`, which holds the challenge constant and
changes the credential, and four `aad-only-stepup-` negatives that hold the credential constant and change one
challenge field each: the label, the version, the transition id, the nonce.

**Every one of the four makes the same move, and it is the move row 9 had to be taught.** An assertion
collected over the wrong challenge, presented unmodified, is refused by a **string comparison** between the
challenge inside `clientDataJSON` and the one the service issued — and that comparison would refuse it just as
readily if the challenge were signed by nobody. So each negative **rewrites `clientDataJSON` to carry the
challenge the service wants**, which forces the refusal onto the signature and is also exactly what a real
attacker would do, since those bytes are theirs to edit. The unmodified replay is published too, as a
**demonstration** rather than a negative, with the message it stops at asserted on every run — because the
value of the four is only legible beside the check they are deliberately not making.

**The ceremony underneath is row 12's and is imported rather than copied.** `scripts/lib/webauthn.mjs` holds

**The embedding policy now lives there too, and that is the extraction earning its keep** (`S0-1`). Neither
verifier read `crossOrigin` or `topOrigin`, so a step-up assertion collected in a delegated iframe — this

**Two structural assertions do work no example can.** The generator counts the preimages of every symbol and
requires exactly eight, which is the 125-bit claim itself rather than an illustration of it. And each
