# Selection — TRD §15 row 13: device-lock derivation, enrollment migration and copy

**Amended 2026-10-14:** the new authenticated automatic Local mode restores credential-free first use.
External-factor protection is optional for Local and required for sync. Existing protected workspaces
retain their factors. The opt-in transition copies complete CRDT state to fresh encrypted custody and
content, verifies before retiring the automatic predecessor, and is resumable. [SC-08](../storage-contract.md)
and TRD §13.3 supersede the September requirement for a human-held code at every Local genesis.
No ordinary disable-protection or persisted remember-unlocked capability is introduced.

**Amended 2026-09-08:** mandatory factor custody at persistent genesis/cold start replaces the optional
default. [SC-03/04/08](../storage-contract.md) governs writer lifetime, migration and copied-profile claims.
Factor seal/derivation bytes stay unchanged; custody lifecycle metadata is versioned separately. The
[conformance matrix](../storage-conformance.md) records production tests still required.

**Status:** selected, and folded into the TRD. **Date:** 2026-08-18
**Closes:** TRD §15 row 13 · **Scope of:** review 3a (storage and journal)
**Constrained by:** TRD §13.3, §13.4, §13.2, §6.1, §6.5 · PRD §7.2, §6.7 · **Stage:** [sequencing.md](../sequencing.md) §3.1
**Vectors:** [`test/vectors/device-lock.json`](../../test/vectors/device-lock.json), generated by
[`scripts/generate-device-lock-vectors.mjs`](../../scripts/generate-device-lock-vectors.mjs)
**Companions:** [row 3](./row-3-record-format.md) selects the envelope whose custody this changes, and hands this
row the question; [row 14](./row-14-recovery-code.md) selects the code generator reused here verbatim;
[row 1](./row-1-algorithm-suite.md) selects the primitives.
**Amended by:** [`S0-2`](../review/remediation/S0-2/README.md) (2026-08-27) — enabling the lock **replaces the wrapping credential** rather than only reseal the envelopes
(TRD §§13.4, 13.7). `L_lock` protected the `KeyEnvelope` and left a promptless credential beside it, so a pre-lock
profile copy could open the reader wrap a later rotation published. The custody record gains that credential, and
`rotation_owed` is derived from the apply record rather than asserted.

## The selection

```
Custody, per principal/workspace entry within its local user slot

  CustodyRecord = { v: 2, state: 'creating' | 'migrating' | 'protected',
                    principal_id, workspace_id, seals: LockSeal[],
                    creation_or_migration_intent | absent, seal_reserved,
                    rotation_owed: boolean, wrapping_credential: {
                      id, custody: 'staged' | 'factor-sealed',
                      sealed, predecessor_id | absent } }

  New genesis    confirmed code, factor seals of fresh L_lock, sealed generation
                 and receiving keys; state 'protected' only after durable completion.
                 No L_local and no persistent acknowledgement before completion.

  Migration      v1 promptless/enrolling records are legacy input. Preserve old
                 custody until verified resumable replacement is durable. Never
                 treat missing/partial custody as fresh or create a promptless fallback.
                 Existing factor-sealed v1 entries require verified complete receiver
                 custody and a fresh root when seal-reservation history is absent;
                 never infer that history from stored envelopes.

  Scope          factor bytes retain their principal/workspace binding. The shared
                 lifetime barrier is local-user-slot-wide; that coordination scope
                 does not widen a factor's cryptographic authority.

The factor seals

  LockSeal = { v: 1, factor: 'code' | 'prf', id, salt: Uint8Array(16),
               nonce: Uint8Array(12), ct: Uint8Array }
             ct = AES-256-GCM(K_factor; plaintext = L_lock, 32 bytes)

  K_factor = HKDF-SHA256(ikm, salt = salt,
                         info = LP("done/devicelock/v1") || LP(principal_id)
                                || LP(workspace_id) || LP(factor), L = 32)

    code     ikm = utf8(canonical code). Row 14's generator, alphabet and
             normalizer, unchanged: 125 bits, generated, no stretching.
             id = "code". Always enrolled.
    prf      ikm = the 32-byte WebAuthn PRF output.
             id = the credential id, base64url. Optional, any number.

  AAD      = LP("done/devicelock/v1") || LP(principal_id) || LP(workspace_id)
             || LP(dec v) || LP(factor) || LP(id)

The PRF evaluation input, which is where the separation lives

  prf.eval.first = SHA-256( LP("done/devicelock-prf/v1")
                            || LP(principal_id) || LP(workspace_id) )

  One assertion yields one slot's key for one role. §13.4's other three factor
  roles differ here, in the input, not in an HKDF label afterwards.

Genesis and legacy migration

  Genesis        confirm generated code; stage custody/identity under one creation
                 intent; complete durable genesis before the first acknowledged edit.
  Migration      acquire exclusive slot permit; stage new L_lock and retained-key
                 seals; replace every promptless future-content receiver; atomically
                 swap custody where its records share a database; apply the verified
                 successor through resumable SC-03/04 phases. Old references retain
                 their openers. Protection pending until required phases complete.
  Disable        not offered; no ordinary promptless downgrade.
  Add/remove     add an authenticated seal or remove one while another valid factor
                 remains. No content-key change solely for a non-exposure seal change.
  Last seal      removal refused. Exposure-driven replacement uses the selected
                 forward-generation transition and cannot erase earlier copies.

                LP(s) = uint16be(byteLength(utf8 s)) || utf8 s
```

`seal_reserved` belongs to the identified custody root and monotonically counts every AES-GCM
invocation under it, across purposes and abandoned attempts, before encryption (row 3 §5, SC-09).
A transition intent identifies the staged root and its counter; an interruption never resets that count.
`protected` requires verified complete genesis/migration and no remaining creation/migration intent;
otherwise the durable intent identifies the operation and completed phases needed to resume. The
`rotation_owed` flag is derived from that operation, not evidence that its prerequisites completed.

Everything below is why, and what it cost.

---

## 1. The threat model is row 14's inverted, and it decides the factor

Row 14 turned on one sentence PRD §7.6 had already written: **server-held sealed data permits offline
guessing.** That fixed the threat model and reduced the row to a number.

**Here the same sentence applies with the word _server-held_ deleted, and that makes it stronger rather than
weaker.** The seal that a device-lock factor opens lives in the profile, beside the ciphertext it protects.
An attacker holding the profile — which is the entire scenario the lock exists for, §13.3's list of an OS
backup, a disk image, a synced profile directory, a forensic tool — holds the oracle too. Every guess is
offline, unrateable and free. Row 14's attacker had to fetch an envelope from a service first; this one has
already finished fetching.

**The selected response is a generated 125-bit code**, not a user-chosen password. Its entropy is the
basis for resisting offline guessing; an online attempt counter cannot rate-limit an attacker holding
the seal. PRF adds another seal where the authenticator capability remains external to the copied profile.
Its availability and user-verification behavior require platform evidence. This does not justify blanket
claims about hardware, filesystem forensics or other disk-encryption products (SC-08).

---

## 2. Why the code is mandatory rather than the fallback

The obvious design offers PRF where the platform has it and a code where it does not. It is one line shorter
to describe and it is wrong twice.

**§13.4 already holds the value: _PRF's optionality is not a product branch_.** It says so about device
credentials, where the reason given is that the code is mandatory, so an authenticator returning no PRF result
"costs its owner an optional convenience wrap and nothing else: no branch, no device-dependent product
surface". PRD §7.6 builds the recovery keypair the same way — the code is the root, and PRF-capable passkeys
are "additional independent seals". **Making the code the root here is not a new pattern; it is the second use
of one the project already chose.**

What it buys concretely: one enrollment flow, one set of copy, one failure mode, and a lock whose behaviour
does not depend on which browser the user opened it in. Where PRF exists the user touches a sensor and the
code is a thing they filed; where it does not, they paste the code. Neither is a different feature.

**The indirection through `L_lock` is what makes that affordable.** If each factor sealed the `KeyEnvelope`s
directly, every factor would cost a reseal of every retained generation, and enrolling a second passkey would
be a migration. With a random `L_lock` in between, a factor is one 32-byte seal — add, remove, replace, all
O(1), none of them touching content or content keys. **Changing the code does not re-encrypt anything**, which
is also what makes it something a user can be told to do.

**The cost, and it is real: this is a third code.** A user with an account and two locked devices files a
recovery code and two device-lock codes. That is named here rather than discovered in support, and §7's copy
answers it by making the recording ceremony proportionate: at an account workspace the device-lock code is
shown and may be skipped, because re-enrolling a device is the ordinary path and the workspace is not at
risk. At a never-admitted Local workspace it is confirmed by transcription, because there it is the last
readable replica and PRD §7.2 already says so in those words.

---

## 3. Domain separation has to happen inside the PRF input

§13.4 requires four factor roles to stay distinct "even where one authenticator ceremony supplies more than
one", with outputs "domain-separated and never substituted": the account authenticator and slot verifier, the
device-key PRF, the content device lock, and any recovery-factor PRF.

**The natural way to satisfy that sentence does not satisfy it.** Evaluate the PRF once, then derive each
role's key with its own HKDF `info`. The keys are distinct, the labels are explicit, and the property is still
broken: whoever holds the PRF output holds all four. An assertion the user approved for _unlocking a signing
key_ yields, in the same variable, the material that opens content. The separation has to be upstream of the
value, not downstream.

**So the role and the slot are inside `eval.first`**, which WebAuthn hashes into the credential's PRF
evaluation. Two roles are two different inputs and therefore two unrelated outputs; an assertion collected for
one is worth nothing for the other, and that is true of the collected bytes rather than of the code that
handles them.

**Putting the slot in there too costs nothing and buys the §6.5 property.** One assertion produces one slot's
key. A profile holding an anonymous Local workspace beside an account workspace — PRD §6.7's ordinary path,
not an attack — has two locks and two unlock ceremonies, and neither ceremony ever materializes a value that
covers the other. This is not a hardship at cold start: §6.5 enumerates slots through the index rather than by
opening them, and the app opens the workspace it is showing.

## 4. Genesis and resumable legacy custody migration

New persistent workspaces use confirmed factor custody directly. The code ceremony and the durable
creation record precede acknowledgement; SC-06 classifies partial and concurrent creation. Custody roots
retain this row's principal/workspace scope inside the owning user slot. The slot-wide lifetime barrier
coordinates transitions without broadening the scope of a factor.

Existing promptless keys cannot be exported and resealed. Generate new factor-sealed custody and
replacement future-content receivers, not just new envelopes beside an old promptless receiver. Stage
retained-generation envelopes, durably swap custody, then complete the required certified receiver and
forward-generation transition. Use SC-03/04's exclusive permit and restart records. A suspended writer
can delay progress; no timer or steal authorizes retirement.

The same-database custody swap is atomic; work across databases is resumable. Never delete a required
opener before its replacement completes. After a transition worker dies, reacquire exclusion and
re-evaluate current carriers rather than trusting its old census. `rotation_owed` is derived from
unfinished required migration phases, not cleared merely because the factor was confirmed.

## 5. Legacy migration rotates forward and does not erase history

A pre-migration copy retains its old `L_local`, receiving credentials and `K_g`. Resealing current local
envelopes cannot remove those copies. Replacement receiving credentials and a successor generation
prevent that old receiver obtaining future keys after the required transition settles. Fresh protected
genesis has no promptless predecessor.

Service settlement, observation and local activation are distinct (SC-03). Other devices may use an old
generation until observing its successor. The UI reports protection pending until applicable durable
migration predicates hold and does not promise instantaneous global protection or retroactive erasure.
A migrated profile can retain factor-sealed openers for old history while removing only predecessors
whose references permit retirement. Account migration uses the ordinary certified-set/generation
protocol; Local's corresponding transition needs no network service.

## 6. What Stage 1 owes

Stage 1 includes confirmed factor genesis, cold-start unlock, explicit partial-state handling and
factor-protected future receiving credentials where present. A record that says promptless while
waiting for a later stage is no longer conforming. The selected factor cryptographic formats remain;
new custody metadata has an explicit version and legacy conversion path.

Existing vectors prove seal bytes and separations only. Production first-run, copy, migration and
writer-lifetime obligations are C04–C06/C10–C14 in [storage-conformance.md](../storage-conformance.md).
No plaintext scan or non-extractable-key flag pays those obligations.

## 7. The copy

**At first run:** save and confirm the generated device-lock code before persistent editing. Explain
that it opens this device's local copy, is not account authentication or account recovery, and must be
kept outside the copied-profile exposure domain. Do not retain it for redisplay. Code-only unlock works
offline; offered authenticator seals are additional conveniences.

**Local consequence:** if this is the last readable copy and the last factor is lost, the data may be
lost permanently; the app and support cannot open it. **Account consequence:** login alone does not
recover content; a surviving authorized device or the separate user-held recovery material is required
to re-enroll. Recovery does not unlock the old slot implicitly.

**Cold start:** offer enrolled factors only, with a concise wrong-code refusal. There is no ordinary
“disable lock” action. Factor removal requires another valid enrolled factor; replacement for exposure
uses the forward-generation rules.

**Migrating an existing installation:** report protection pending until durable custody, receiver and
generation completion. Earlier copies retain their old history, and remote devices can lag observation.
Do not promise secure erasure, resistance to live hostile code after unlock, or all OS forensic artifacts.
Supported-browser full-profile tests establish the bounded copied-profile claim in SC-08.

## 9. What is still open, and what Stage 4 owes

~~**The PRF availability floor is asserted, not verified — the same gap row 1 recorded for Ed25519, and it
should be closed once for both.**~~ **Closed on 2026-08-19**, in TRD §10.11, and closed once for both as this
row asked. The answer for PRF is not the one the phrasing expected: **there is no floor to state.**

**PRF's availability is not a browser version, so no version can be named.** It is a matrix of operating system,
browser and authenticator kind — Baseline has no feature for PRF or for any WebAuthn extension, and roaming
authenticators cannot be reached from iOS or iPadOS at all, because the platform does not pass extension data to
external keys whatever the key supports.

**Which is a result in this row's favour rather than an obstacle.** §5's argument was that PRF's optionality must
not become a product branch, and that the code has to be the root; a capability whose availability is this ragged
is precisely one that cannot be a root. **A design that had made PRF the root would need a floor that does not
exist.** The gap this row recorded was real, and closing it strengthened the construction rather than qualifying
it.

**Remaining validation is explicit.** Required-browser lifetime and authenticator behavior, complete
credential inventory, first-run/last-factor-loss UX, and production migration/copy tests remain pending
in C04–C06/C10–C14. These are not reasons to restore the old optional default. Review 3a consumes this
corrected contract; row 12's separate slot-authentication role remains in review 3b's scope.

**One thing Stage 4 must not do**, written here because it will be tempting there: the recovery path may not
be given a way to open a locked slot. §13.3 forbids the lock becoming a recovery factor implicitly; the
converse is the live risk, and it looks helpful. A device whose factor is lost re-enrolls as a device. It does
not get its local custody unwrapped by `R_priv`, because a lock that recovery can bypass is not a lock — it is
a preference, and the copy in §7 would be a lie.

## 10. The vectors

`node scripts/generate-device-lock-vectors.mjs` writes them; `--check` fails if they are stale. The generator
verifies itself on every run: every seal round-trips, every negative fails, and the published must-fail list is
compared against what was actually asserted in both directions.

**Four kinds, and the second is the one that only exists in this row.**

The **seal vectors** pin `K_factor`'s derivation, the AAD and the framing, for both factor kinds. Two seals of
the _same_ `L_lock` under a code and under a PRF output, which is the multi-factor property made testable: an
implementation that accidentally makes the two factors open different keys passes every single-factor test.

The **separation vectors** pin `eval.first` for the content device lock against §13.4's other three roles and
against a second slot, and assert all of them differ. **That file is the only place the §3 argument becomes
checkable** — the property is about the value WebAuthn returns, so it cannot be tested from ciphertext, and an
implementation that regresses it produces working locks with no visible defect.

The **custody vectors** show the same `KeyEnvelope`, with row 3's AAD byte-for-byte unchanged, opening under
`L_local` as legacy migration input and `L_lock` as current custody, and assert separately that `L_local` does **not** open the
lock tier's envelope — which tests one envelope substitution only. It does not establish absence of every copied-profile
opener, mandatory genesis, or protection of future receiving credentials. That is row 3's _"the format is deliberately indifferent to
that choice"_ asserted rather than believed, and it is what a reviewer needs in order to check the two rows
against each other in one place.

The **negatives**, thirteen, in two groups — **and the split is a correction rather than a tidy-up.**

The _derivation_ group changes an input to `K_factor` and fails because the key is wrong: wrong code, wrong PRF
output, a code seal opened as a `prf` seal and the reverse, a seal moved to another workspace, a seal moved to
another principal, a flipped tag bit, a truncated ciphertext.

The _AAD_ group keeps the correct key and changes exactly one bound field, so it fails on the binding alone:
the version, the credential id, the factor, the workspace and the principal.

**The second group exists because the first one was not proving what it looked like it was proving.** `factor`,
`principal_id` and `workspace_id` are bound in the HKDF `info` _and_ in the AAD, and the obvious negative
changes both at once — so it passes whether or not the AAD binds anything. Deleting `factor` from the AAD
entirely left every negative in an earlier draft of this file still failing correctly. **The rule this row
adopts, and offers to the other three selection documents: every field in an AAD needs a negative that changes
that field and nothing else**, or the binding is decoration that happens to sit next to something that works.
The generator is now mutation-checked against exactly that — dropping any one of the five fields from
`aadForSeal` makes a published negative open.

**The code path is not re-derived here.** Row 14's alphabet, mask and normalizer are reused, and the generator
asserts they still match row 14's published vectors rather than copying them — if the two documents ever drift,
the build fails instead of shipping two incompatible encoders under one name.
