# Additional-device approval progress

The additional-device screen reports work from the live coordinator while its existing operation is running. Progress is presentation only. No stage, count or callback return value can authorize a transition, select a key, complete the human comparison or establish certification. No progress is persisted, sent to the service, or used to change retry behavior.

The indicator distinguishes checking the saved snapshot and source inventory, verifying synced changes, checking journal-inclusive local writing, preparing and publishing the new snapshot, delivering approved access, installing access and verifying certification. The source and change counters advance only after the corresponding verification and application finish. Totals come from the authenticated source list and accepted cuts after validating baseline coverage; an unsafe aggregate integer omits the total. Completing a counter completes that substep only, not the connection. Work with no known count uses an indeterminate indicator.

Observers receive stage names and numeric counts only, never writing, identity, keys, comparison input or signed payloads. Observer exceptions are isolated from the protocol. Source lifetime checks run before observations; the coordinator suppresses observations after abort and clears progress on success, failure and close. Navigation clears the UI immediately. Resumption starts a fresh display for the exact saved attempt. It does not claim that interrupted replay was checkpointed.

The screen also explains when it is waiting for the new device to save and confirm access. It asks the person to keep both devices open. This does not promise execution while a phone is locked. There is no activity timer, additional polling, new request, wake lock or service-worker task. Existing notifications and refresh scheduling are unchanged.

## Further performance work

The existing [cold-source census](performance-experiments/2026-10-11-account-cold-census/README.md), [authority authentication reuse](account-authority-authentication-reuse.md), [prepared remote handoff](account-prepared-remote-handoff-design.md) and [cooperative retention preparation](performance-experiments/2026-10-13-retention-handoff/README.md) offer applicable patterns: parse once within a verified inventory, reuse only exact authenticated bytes within their owner, and yield between splittable operations while rechecking lifetime.

`withNativeHistorySource.local()` already uses the baseline's authenticated census when available. The independent `readHistorySource` reconstruction proves accepted-prefix and source completeness; the local reconstruction additionally includes journal-only writing. An editor document cannot substitute for the first proof. Existing memo/selection evidence is private to its storage owner and cannot simply be carried into an enrollment owner. Ceremony login ownership also forbids overlapping calls, while inbound observations must remain monotone.

The receiver’s [`collectReceivePages`](../src/crdt/receivePrefetch.ts) also demonstrates bounded prefetch: ordered consumption, reserved byte capacity before launch, and cancellation/drain of unwanted tails. Enrollment cannot directly launch concurrent `withLogin` calls. A candidate could overlap a bounded next fetch with verification after login ownership is released, but would need independent controls for partial groups, monotone observations, expiry, exact cut bounds and draining on failure. This is a candidate design, not implemented or measured here.

The next speed experiment should separately attribute accepted-history network replay and local recovery on a deep original and joined account, including any installed history checkpoint. Compare verified work counts as well as latency before selecting owner-local reuse or cooperative yielding. Preserve changed-inventory, competing-authority, expiry, cancellation and exact-resumption counterexamples. No further speedup or phone bound is established by this presentation change. The preceding [bounded transport result](performance-experiments/2026-10-16-device-approval/README.md) retains its own measured scope.
