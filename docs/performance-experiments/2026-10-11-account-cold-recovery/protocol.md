# Reuse within preliminary Account recovery

Recorded before implementation. Baseline: signed `4bcac419` plus both retained uncommitted cold-open repairs (linear prefix/shared census, then one parse per source census). The current matched deep-history median is 3.44s.

Hypothesis: preliminary recovery's initialize and subsequent load authenticate the same immutable store twice. Enable existing lifetime-local opened-record reuse only for the Account recovery calls, and remember successful validation only for that content owner's exact authenticated snapshot identity. Every load still rereads storage, authenticates its counter and checks placement/ciphertext equality. Any difference receives a new identity and full validation. Journal reads stay fresh. Validation failure/cancellation cannot install reusable success; dispose clears plaintext and the remembered identity. No shared cache or ownership handoff, no change to live-editor verification or stored/wire formats.

Prediction: one preliminary full verification instead of two, two complete delivery/inbound passes instead of three overall, unchanged five physical reads, about 4,100 fewer native decryptions on the 3,830-row deep fixture, and approximately 0.4–0.7s lower opening time. Receiver history should benefit too, as its signatures are also verified once less. These estimates are uncertain; compare actual work and elapsed time independently.

Use the same private deep, received-page and fresh fixtures. Five alternating deep pairs and three pairs for each guardrail, offline after asset caching; virtual factor unlock included, human entry excluded. One separately profiled run and ordinary-build edit/reopen checks. No simultaneous CPU-heavy work of ours during primary timing. Preserve every run and exact runtime patches; credentials stay private. Report medians/ranges, work counts, collected heap and first edit, not population confidence or phone claims.

Focused safety tests must exercise the real recovery helper and content owner: opt-in versus unchanged default, no reuse across calls, ciphertext/counter/row changes between initialize and load, semantic refusal when a row disappears, journal additions after the first read, failed validation and cancellation with late completion, and buffer cleanup. A deliberately weakened identity check should expose the otherwise-refused changed snapshot. Retain existing native corruption, pending-update, journal recovery, retry and cancellation regressions. No generalized fault campaign or release-validation resumption.

Adopt with at least 10% improvement in the matched deep median, expected complete-pass reduction, successful boundary tests, no material receiving/fresh regression or retained-memory growth. Report the 2.5s budget separately; do not infer success from relative improvement. The previous two slices stay intact and uncommitted.
