## Ownership and acknowledgments

The worker owns the existing slot permit, account keys, native content I/O, verification caches, canonical workspace and serialized owner operations. Window owns its actual localStorage endpoint and native passkey UI. Current cryptographic and native checks still run inside the original owner. Owner incarnation plus strictly increasing bounded request IDs bind every command/reply. Closing invalidates all pending UI replies immediately, before awaiting worker drain; a shared liveness word adds refusal at the existing SessionTask step/wait gate. A closed/replaced incarnation cannot publish a late result. A close acknowledgment follows real owner cleanup and permit release. Forced termination is context loss, not successful graceful cleanup. A command canceled after a durable journal write has an uncertain acknowledgment: recovery may retain it, and no automatic resubmission is allowed.

This feasibility kernel uses a bounded shared-memory storage mailbox: only the worker may wait; Window never waits or performs account verification for it. Every journal read/write goes to fresh actual Window localStorage, not a captured or authoritative-looking copy. Shared memory requires isolation headers supplied ONLY to /worker-lab/ in the disposable server. This is a laboratory adapter, not a selected cross-browser product mechanism or changed production header policy. Preserve an explicit production decision: keep a small same-handler Window journal/admission bridge (preferred initial target), or separately design an accepted/pending protocol. An asynchronous worker reply cannot stand in for the existing same-handler synchronous local acknowledgment. Do not activate this prototype as the editor.

Window activity/passkey calls remain explicit endpoints. The lab binds accountCapture's existing lifecycle references to a worker-local EventTarget driven by host lifecycle messages; it does not fabricate a global DOM or bypass authority checks. An additional liveness check is inserted at writeSession's existing synchronous effect gate. All verifier/crypto/storage-owner bodies otherwise remain byte-identical. Local/service automation and warm audit scheduling are off in the manual proof; the owner still fully verifies its native account and writes through the existing journal/content path. This cannot claim final-client performance or automate service history.

## Native-permit and termination correction after the first controls

The Window storage endpoint also needs its own actual shared slot lifetime, held until worker drain/context loss settles. A worker permit alone cannot fence a Window callback queued just before unexpected worker death. The prototype now acquires the existing Window openWriteSession and uses its write guard for actual journal effects; external exclusive operations must wait for BOTH permits. Retirement closes both. Termination invalidates the shared liveness word, wakes any pending mailbox, terminates the worker and releases the Window permit; no graceful-erasure acknowledgment is fabricated. The initial abrupt-loss control failed its5s permit-release guard with a blocked mailbox; preserve it. A separate harness defect left a10s fallback reading the next test's mutable output path and stopping its server; capture the old container ID and cancel that fallback on exit. Preserve the original teardown failures, including cases whose inner assertions passed. No application implementation or old repository test changes.

The first dual-permit build correctly refused an unexpected second cleanup-observer transform in the Window dependency closure. The outer command did not stop on that build failure and began tests against the previous artifact; interrupt and preserve that run as invalid, not candidate evidence. Subsequent launchers require a successful closed input/asset identity before running, with strict sequential build failure handling. The expected observer cardinality is now1 lifecycle binding,2 added liveness guards and2 cleanup observers (one main/one worker). Main still does no account validation: its added import is the existing slot lifetime/compatibility owner.

The next attempt refuses all nine cases at the generic Window compatibility check: generic shared sessions deliberately reject these private Account markers, and private account sessions actually request an EXCLUSIVE slot permit. Preserve the refusal; do not weaken that compatibility check or merely acquire two copies of the existing account permit. The lab's revised topology is explicit: the Window supervisor holds a new exclusive reservation, drains the existing slot name with an exclusive barrier, then acquires a shared endpoint lease; the worker acquires a real shared lease on that same existing slot name. Only in this lab build are the two private account acquire-mode literals changed to shared. All actual account compatibility/authentication/crypto/native checks remain. Other new supervisors serialize on the reservation AND must drain surviving old workers through the exclusive barrier. Old exclusive account/removal owners still wait for both existing-name shared leases. Generic older shared Local owners still refuse Account markers. No production acquire mode or storage marker changes. This is a new protocol proposal with native-browser falsifiers, not a claim that two shared owners alone preserve exclusion.
