# Phase162 — sustained Goals typing and unlocked return: diagnostic protocol

2026-10-28. User reports new whole-app stalls in released b6f0160a during seven-sentence Goals typing at about80wpm and when returning to an unlocked phone app. Decision: identify blocking work and a defensible worker boundary before changing runtime behavior. Retain separate download, verified-durable and presentation queues as the agreed direction; this diagnostic does not implement them.

## Design, units and measurements

Mechanism-finding benchmark, not a population estimate or release-regression causal comparison. Use the exact retained production frontend b6f0160a, current byte-matching runtime modules, a copied fictional persistent synced H2 account and its real service/IndexedDB/virtual passkey owners. Existing private fixture has5,000-character Goals and retained history; never access production or real browser profiles. One independent copy per journey. Characters within a journey are correlated, not independent replications.

Fixed order: desktop without CPU profiling; fresh desktop copy with CPU profiling; fresh mobile-emulated4x copy without CPU profiling. Each types the same seven-sentence paragraph by trusted CDP key events offered independently of renderer acknowledgments at150ms/character (80 standardized five-character words/minute). Do not speed up missed deadlines or skip characters. Record offered times, event counts/trust/focus/visibility, complete final text, per-input handler/paint delay, p95/p99/max, all long tasks,16ms heartbeat gaps, network method/path/status/timing without bodies, page errors and exact asset/source identities. Keep16ms local and2.5s peer acceptance gates unchanged; this single-device diagnostic cannot award the peer gate or release acceptance.

Then allow20s foreground idle, freeze the unlocked target for20s through real CDP lifecycle, resume/bring it to front, offer one further character promptly and observe20s. Record actual visibility/lifecycle events; if the browser does not establish a hidden/frozen/visible transition, label that coverage unestablished. This approximates suspension/return, not physical Android background behavior or every simple focus transition. No synthetic dispatchEvent lifecycle substitutes.

Profiled run is attribution only, excluded from timing acceptance. Use1ms CPU sampling with actual bundle maps; sample residence and long-task overlap identify suspects, not exact per-function exclusive runtime or a causal speedup. No production-value capture, command replacement, skipped verification or bypassed storage admission.

## Decision and stop rules

Retain all runs and apparatus failures. Stop a journey on lost/duplicate input, wrong final writing, storage/authority/owner failure or resource refusal. Run the three planned journeys once; add only an explicitly documented discriminating control after source attribution. A>=100ms task/input delay selects a candidate for trace/source analysis, not a new acceptance budget. A negative result narrows only this fixture. Resolve coarse timer/profiler overhead and validate event denominator before attributing. No inferential power claim: three diagnostic trajectories cannot estimate the frequency of users' stalls. Physical device, OS/keyboard and real account-shape differences remain limits.

## Runbook and preserved contracts

Fresh private directory/service state/profile for each run; server1CPU/1GiB with existing cgroup guards and unchanged real account protocol. Retain byte identities for frontend, source modules, helper closure, browser executable, observation code and workload. Never upload fixture storage/credentials/profile/service state. Verify exact final Goals, lock/reopen persistence and Undo after observations. Preserve main-thread journalling, all authority/history/witness/commit checks, local flushing/backoff, service automation0 and original finite acceptance evidence. No merge, deployment, release preparation, main-preview changes or computer use.
