# Read-only design: one signed multi-publisher tip

No endpoint, signing purpose, durable format or cache is built here. This is a contract proposal, not measured performance or authority to skip verification.

Current read-v2 authenticates the request and current workspace/reader/publisher authority before capturing the live publisher ledger, verifies its census/witness, then rechecks current state and authorization inside the commit/signing boundary. Its empty signed page binds the exact request and certifies that the selected cursor is at the verified through position. The batch endpoint currently invokes this per request; it is not one signed aggregate or one logical read. With hints withheld, those quiet reads are discovery and cannot simply be removed.

A new purpose could sign a closed canonical vector once, with these requirements:

1. Exact request binding: new domain/version, digest of the original reader-signed request, service ID and origin, workspace, lineage, membership head/epoch, reader identity, nonce, expiry and ordered queried publisher/cursor set. Each response item identifies its publisher, verified through position and accepted-prefix identity (or an explicitly equivalent witnessed tip). No ambiguous duplicate IDs, extra fields, alternative encodings or guessed empty state.
2. Completeness: define whether this is the complete current authorized publisher roster or exactly the requested set. Include and authenticate the roster/history revision and explicit removed/retired/pruned/unavailable states. An omitted or unauthorized publisher never means unchanged. A stale roster must trigger authoritative rediscovery; a discovery hint alone cannot retire a publisher or erase a pending read.
3. Fresh authorization and history: authenticate the current reader and every requested publisher's history/role before live-tip capture, preserving removed writers' readable history. Then capture verified ledgers after that potentially expensive verification. At the signing boundary recheck reader authorization, current authority/head, custody, request expiry and every captured ledger/witness identity. Avoid holding a fragile live publisher snapshot across crypto. Bound retry and return explicit refusal when state changes.
4. Snapshot semantics: either sign one atomic vector or explicitly sign independently validated item snapshots with well-defined freshness. No fiction of global order across independent publisher chains. Compare each tip monotonically with the locally authenticated prefix and previously observed tip; regressed or conflicting results are not quiet. A server tip never advances the client's accepted position or authorizes application of absent bytes.
5. Bounded work/account fairness: one signature and HTTP exchange can replace N framing/signing/round trips, not N authorization, history or ledger obligations. Charge logical publishers/work, bytes and active slots; cap vector size/expanded work, retain admission/backoff and cross-account fairness. Do not turn a single token into unbounded publisher scans or leak another account's inventory. A bounded partial response needs explicit continuation/completeness semantics.
6. Client semantics: verify exact request/signature/canonical response/expiry and current authority, then update only short-lived discovery evidence. Changed publishers use normal signed pages, entry signatures/decryption, chain, witness, committed-state coverage and commit checks. Invalidate evidence on hints, authority/owner change, clock rollback/expiry and lock. No persisted trust or shared process authority cache follows from the vector.
7. Liveness: keep bounded scheduled discovery/repair when hints are withheld. Batching quiet checks reduces exchanges; it does not remove the post-drain idle interval or the need for R-like repair. A positive vector result must lead to a fair productive read. A stale valid negative response cannot suppress discovery beyond its original freshness budget.
8. Compatibility/rollbacks: advertise an exact capability and new signing domain. Missing/unsupported endpoint must fall back to the existing owner-wide discovery path, preserving bounds; authorization/integrity errors must never be interpreted as quiet or unsupported. Define stale-tab and older-server behavior, custody sign-only purpose, test vectors and rollback before landing.

Tests before implementation/landing: withheld hints with no backlog and after drain, missed last hint, membership change during verification/signing, concurrent publisher writes, revoked reader, removed publisher, incomplete/duplicated vector, stale request/clock rollback, tip regression, pruned history, owner cancellation/erasure, bounded large roster and multi-account contention. Exact tip completeness must have an independent oracle. This could replace per-publisher *quiet discovery exchanges*; it cannot replace signed data verification or make independently ordered publishers one commit chain.
