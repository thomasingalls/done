# Park incremental publication; keep the selected combination

The final candidate passes its directed/generated/differential/fault controls and all six browser
sessions. It demonstrably skips unrelated card-body reads in the controlled module fixture while
retaining detached output, normalization, fallback and current history counters. That removed work
does not translate into a persuasive application gain in this fixed screen.

Ordinary early median effects are a 9.0% improvement and an 11.3% regression. Later medians regress
3.7% and 21.0%, with p95 regressions of 9.3% and 27.1%. Median paired ratios give 1.1% early /12.3%
later median regression and 0.3%/18.2% p95 regression. The Unicode guard is also slower in both
blocks. The small session count and host/JIT/GC variation limit magnitude and causality claims;
these data support declining selection, not a universal claim that incremental publication is slow.

Preserve the incremental and complete patches, all positive/negative observations and the new
normalization/history/aliasing controls. Keep R3 preparation reuse + comparison pool + editor
shortcut + primitive value-string reuse + membership-repair eligibility as the selected combination.
Optional UI and older publication patches remain separately available. This is not a rejection of
small incremental gains: this implementation fails to show a consistent gain in its tested setting.

No profile was taken, so public whole-snapshot cloning, cache/header maintenance and other remaining
work are possible explanations, not measured attribution. The candidate still performs a detached
whole-snapshot clone and does not implement selective UI subscriptions or stable public identities.
A future publication attempt should change or measure a specific remaining cost before repeating
this design's timing. More correctness coverage alone would not establish a performance benefit.
