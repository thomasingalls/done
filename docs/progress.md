# done — Active slice

**This file is disposable, and that is its function.** It holds the slice of work that is active right now
and nothing else. Nothing of record value lives here: decisions go to [decisions.md](./decisions.md), and
closed work goes to [completed.md](./completed.md).

## How this file works

**Everything below the rule is replaced wholesale when the active slice changes.** Not amended, not struck
through, not archived in place — deleted and rewritten. A working document that accretes is a working
document nobody reads, and the two files that _are_ records already exist.

**One thing must happen first.** When a slice closes, write its outcome into
[completed.md](./completed.md) _before_ rewriting this file. That ordering is the only thing protecting
the record, because after the rewrite the evidence is gone.

**It grows a tree when the slice deepens.** If work goes deeper without the slice changing — an item turns
out to have four parts, one of which has three — nest it. Nesting is free and says something true about
the shape of the work. What is _not_ allowed is a second top-level slice: two active slices means the file
has stopped answering the question it exists to answer, and one of them is really next-up.

**Status vocabulary**, deliberately small: **not started** · **in flight** · **done** · **blocked** (which
must name what it is blocked on).

**Being wrong here is cheap.** This file is allowed to lag by a day. It is not allowed to describe a slice
that is no longer active.

## Active slice: Stage 0 — select, measure, book

**Status:** in flight · **Plan:** [sequencing.md](./sequencing.md) §3.1 · **Updated:** 2026-08-18

Three bodies of work, almost none of which is application code, all of which get more expensive the later
they start. Stage 1 cannot begin without the first; the last is calendar time that working harder does not
compress. (The harness turned out to need four boot marks in the app — the one exception, and about 100

### 1. Select TRD §15's storage-review scope — in flight

What Stage 1 cannot begin without, and now also what review 3a reads in the week of **2026-08-24** (item 4).
Each row needs a construction and test vectors rather than an intention. Selections live in
[selections/](./selections/), one file per row; every vector file is generated by a self-verifying script and
checked for staleness by `pnpm vectors:check`, which `pnpm check` now runs.

- **Row 1 — the algorithm suite and crypto-agility.** selected — construction with vectors, in
  [selections/row-1-algorithm-suite.md](./selections/row-1-algorithm-suite.md).
  - **Suite 1: AES-256-GCM on every asynchronous path, XChaCha20-Poly1305 on the synchronous one**, HKDF-SHA-256,
    Ed25519, HPKE base with X25519, SHA-256. **Half of this was decided by row 2 and nobody noticed**: §13.10
    forbids sharing a primitive across the two paths, row 2 spent the sync slot on ChaCha, and WebCrypto offers
    exactly one AEAD. The platform decided the rest.
  - **Agility is the half that was genuinely open: a carrier version selects the whole suite.** No per-record
    algorithm field, so no negotiation and nothing to downgrade — and every carrier authenticates its own
    version, so a renumbered record fails to open rather than selecting a weaker suite.
  - **The §13.2 separation rule is machine-checked, not asserted.** The generator buckets every role by path and
    fails if any primitive appears in both. Four published KATs (GCM Test Case 16, RFC 5869, RFC 8032, FIPS 180-4)
    run against WebCrypto on every invocation.
  - **Open:** Ed25519's availability is asserted, not verified — this project has no written browser support
    floor. It is first used in Stage 4, so the row records the gap rather than closing it by omission.
- **Row 2 — the synchronous journal AEAD and its nonce discipline.** in flight — construction proposed with
  vectors, in [selections/row-2-journal-aead.md](./selections/row-2-journal-aead.md).
  - **XChaCha20-Poly1305; 24 random bytes per record; no counter, no durable state.** The width is the
    point: a 96-bit nonce would also hold at this journal's volumes, and that is the objection to it — the
    guarantee would become a claim about application behaviour that a later change can silently invalidate,
    and nonce-reuse faults are retroactive and silent.
  - **The vectors prove themselves.** `test/vectors/journal-aead.json` — the draft-irtf-cfrg-xchacha §A.3.1
    KAT, four composition vectors, six negatives. The generator round-trips every vector and asserts every
    negative fails, on each run, so a "must fail" list cannot quietly stop failing.
  - **Two things before it closes.** The `< 1 ms p95` budget is specified on a **low-end device** and has
    only been measured on a Mac — 7.8 µs p95 at the 18-byte common case, so about 128× of margin, which is a
    strong prior and not the measurement. And it is not yet folded into the TRD. **Sourcing a handset is the
    only item in this slice with a physical lead time.**
- **Row 3 — the encrypted record and local key-envelope formats.** selected — construction with vectors, in
  [selections/row-3-record-format.md](./selections/row-3-record-format.md).
  - **Both formats, because they are one construction a level apart** — the envelope holds the key that derives
    the subkey that opens the records, and §6.1's start-up order makes the dependency literal.
  - **Every cleartext field is in the AAD, and `kind` is why it matters.** IndexedDB holds a structured clone, so
    `v`, `gen`, `seq` and `kind` are editable properties that the load path trusts. A `state` record supersedes
    everything before it, so an editable `kind` is a way to make the store delete its own history through its own
    trim path.
  - **`principal_id` is bound because two principals on one profile is the ordinary path**, not an attack —
    PRD §6.7's anonymous Local workspace plus an account workspace, with no second human involved.
  - **The nonce argument has a different shape from row 2's, and is answered rather than waived.** 12 random
    bytes under NIST SP 800-38D's 2^32-per-key ceiling for random IVs. Row 2 rejected a conditional argument
    because nothing could check the condition; here `seq` already bounds it conservatively in one comparison.
    **This pins something §6.1 left open: `seq` does not reset at trim.**
  - **Eleven negatives, and the must-fail list cannot drift** — the generator compares what it published against
    what it actually asserted, in both directions.
- **Row 14 — recovery-code entropy, generation, step-up authentication and confirmation UX.** selected,
  storage-facing part — construction with vectors, in
  [selections/row-14-recovery-code.md](./selections/row-14-recovery-code.md).
  - **125 bits, Crockford Base32, five groups of five, and no stretching at all.** The row's stated
    question — _does this need Argon2id?_ — turned out to be answered by a sentence PRD §7.6 had already
    written while rejecting passwords: _server-held sealed data permits offline guessing_. That fixes the
    threat model, and what was left was a number.
  - **Stretching is declined on the same grounds row 2 declined a 96-bit nonce.** It converts entropy you
    do not have into time you hope an attacker will not spend; at 125 generated bits there is no deficit,
    and adding a work factor would trade an unconditional argument for one that decays with hardware.
    It also costs a WASM dependency against 43.7 kB of headroom, and this way costs nothing.
  - **The entropy claim is machine-checked rather than asserted.** The generator counts the preimages of
    every symbol under `byte & 0x1f` and requires exactly eight — 256 = 8 × 32 — so a changed alphabet or
    a modulo where a mask belongs fails the build instead of silently producing weaker codes that still
    seal and still open.
  - **The keypair in the vectors checks itself.** It is RFC 7748 §6.1's, and the generator derives the
    public key from the private scalar and refuses to write the file unless they match. An AAD that binds
    a public key to a private one proves nothing if the vector's own halves are unrelated.
  - **Step-up is a bound challenge, not a freshness window**, and that half is drafted for **review 3b**
    rather than closed here — TRD §15 splits row 14 between the reviews and the document respects the split.
- **Row 13 — device-lock derivation, enrollment migration and copy.** not started. **In review 3a's scope
  but not in Stage 1's path**, so nothing but the 24th puts a date on it. **It is now the only unstarted
  row before the 24th.** It will touch §13.3's PRF-or-code framing, which is adjacent to row 14's
  presentation question, so the two should be read together.

_Exit: rows 1–3 selected, with test vectors._ **Met for 1 and 3**; row 2 has the two loose ends above.
**The review's scope is the wider one** (TRD §15): 13 and the storage-facing half of 14 have to be closed by
the 24th as well, even though Stage 1 does not wait on them. **14 is now met**; 13 is not started.

**Four things rows 1, 3 and 14 turned up that are not selections.**

- **The old plaintext `done` database has to be deleted by Stage 1, not orphaned.** Stores get
  per-_(principal, workspace)_ names, so the new code will never open `done` (`src/crdt/persistence.ts:17`) and
  it will sit there full of plaintext content. §11.1's no-plaintext-at-rest test inspects every store, so this
  is a test failure rather than a subtlety — but the kind that gets found at the end of Stage 1 rather than
  planned into it.
- **Row 12 (the slot verifier) is assigned to review 3b, and that is worth a second look.** A local verifier
  resisting offline guessing by a profile holder is storage-shaped, and 3a is the review that will have the
  context. Reassigning it is a change to TRD §15, not something a selection document should do quietly.
- **Nothing was checking the vector files for staleness** — not `pnpm check`, not CI — including row 2's, which
  shipped in the previous commit. All four are now checked together. A stale vector file is a specification
  that has quietly stopped matching its own generator.
- **`recovery` already means something else in the tree, and Stage 4 is about to overload it.**
  `RecoveryCard`, `recoveryCards`, `recoverCardTo` and `src/ui/RecoveryPanel.tsx` are the membership-repair
  surface; `R_priv`, the recovery code and the recovery envelope arrive beside them. Renaming the older one
  is cheap now and gets less so every stage. A naming decision rather than a selection, so it belongs in
  [decisions.md](./decisions.md).

### 3. Build a latency harness and take the plaintext baseline — done

- **Harness for TRD §12's latency rows.** done. `pnpm test:latency` (`test/latency/`,
  `playwright.latency.config.ts`), with `pnpm latency:record` for append-ready rows. Two profiles: desktop,
  and a Pixel 7 under a 4× CPU throttle — emulation alone changes the viewport and the user agent and
  nothing else, so an unthrottled mobile project measures the development machine twice.
- **Record the baseline while the store is still plaintext.** done. **Six of TRD §12's thirteen latency
  rows now have numbers**, in [performance.md](./performance.md). The other seven measure things that do
  not exist yet and arrive with their features.
- **Four boot marks in the app** (`src/lib/marks.ts`), for the one row with no DOM signal — content-root
  load. **That seam is what Stage 1 extends**: the same marks will bracket a key-store read, an unseal and
  per-record decryption. About 100 bytes of initial JS; the bundle went 306.2 → 306.3 kB.

_Exit: a latency harness with recorded plaintext numbers._ **Met.**

**Two things it turned up that are not measurements.**

- **TRD §12's day-to-day navigation row is one row over two paths.** `goTo` (a peek, the menu, `t`) swaps
  the date immediately; `step` (a drag, Alt-Arrow) animates for `SNAP_MS` — 220 ms — and swaps underneath
  once it lands, so its settled figure **cannot be under 100 ms by construction**. §12 does not say which
  path it means, or whether "navigation" is the app responding or the day being in place. A definition to
  settle, not a budget to fail.
- **Headroom is large but not uniform.** On the throttled profile `card focus → editable` is 22.6 ms of
  50 ms and navigation settled is 40.8 ms of 100 ms, against a cold start using 9% of its budget.
